## 和计划的偏差

| 计划中的设计 | 实际 | 原因 |
| --- | --- | --- |
| 模块依赖只规定了“plan 依赖 review 和 knowledge，反之不行” | 写业务代码前补全了所有模块的依赖关系，并规定：review 只通过 kp_id 工作，model_config 归 llm 管理，当前用户 id 从 common 获取 | 其他模块之间的关系没有定论，依赖一旦长出环就很难拆开（决策 002） |
| card_state 有 `reps`、`lapses`，状态中有“新” | 删除 `reps`、`lapses`，增加 `step`；状态只有学习中、复习、重学三种，新知识用 `last_review` 为空表示 | 与 py-fsrs 的状态模型保持一致才能逐条比对；复习次数和遗忘次数可以从 review_log 统计（决策 003） |
| review_log 用 `state_before` 判断是否是新知识 | 增加 `is_first_review` | 新卡的状态也是“学习中”，`state_before` 无法区分“第一次学”和“学习步中”（决策 003） |
| 每日计划按 state 是否为“新”区分到期复习和新知识 | 改用 `last_review` 是否为空、`is_first_review` 是否为真来判断 | 随状态模型的调整而改（决策 003） |
| 使用 FSRS 默认的分钟级学习步 | 项目默认没有学习步和重学步 | 每个知识点是一段几分钟的 AI 对话，同一天重复出现会浪费模型调用（决策 003） |
| 技术方案只写了“Spring AI 2.x” | 固定为 2.0.1 | 这是接入时的最新稳定版，2.1.0 当时还是里程碑版（决策 004） |
| 粒度初稿把“Spring 启动流程”和“Spring Boot 启动流程”作为合并的例子 | 改为“包含不算重复”的例子，分开输出 | 作者标注后的结论：面试中这是两个问题（决策 006） |
| 粒度初稿只有拆分、合并、排序三条规则 | 增加主干、小追问不拆、摘要不越界、包含不算重复四条规则 | 来自人工标注发现的 4 处问题（决策 006） |
| #3 只计划做到“结果便于人工标注” | 在 #3 的分支上继续写了 v4、v5，后来移到单独的 #4 分支 | 标注后直接开始调 prompt，而按 issue 划分这属于 #4。两个提交还没推送时，移到了 `feat/4-m0-conclusion` |

## 遇到的问题

### FSRS 移植（#1）

- **取整方式不同**：Python 的 `round()` 是四舍六入五成双，Java 的 `Math.round` 是四舍五入。间隔恰好是 x.5 时会差一天。改用 `Math.rint`
- **Java 和 Python 的随机数序列不同**：同一个种子无法比对 fuzz 的结果。改为由构造函数注入 `DoubleSupplier`：生成用例时记录 py-fsrs 每次用到的随机数，Java 测试中回放
- **测试有盲区**：变异测试发现，第一版用例对“取整方式改错”和“对学习步做 fuzz”这两类错误发现不了。补充了 `half_intervals`、`long_steps_fuzz` 两组配置，以及一个单元测试
- **线程安全**：`RandomGenerator.getDefault()` 返回的生成器不是线程安全的，而 Scheduler 会被多个请求共享。正式运行时改用 `ThreadLocalRandom`

### 大模型接入（#2）

- **Spring AI 会隐式读取环境变量**：配置中没有 `api-key` 时，它会去读 `OPENAI_API_KEY`，没有 `base-url` 时会去读 `OPENAI_BASE_URL`。解决办法是在 yml 中显式给出两项的值，api-key 默认为空字符串
- **base-url 不会自动补 `/v1`**：Spring AI 2.0 改用 OpenAI 官方 SDK，地址原样使用。连 OpenAI 时必须写成 `https://api.openai.com/v1`，这一点写进了 yml 注释和 README

### 知识点抽取（#3、#4）

- **默认 temperature 下结果不稳定**：同一个 prompt 跑两次，分别输出 29 和 41 个知识点。改为由调用方指定 temperature，抽取用 0.2 后，两次为 33 和 34
- **模型不做跨题合并**：v1 每道题只对应一个知识点。v2 加入示例后合并仍然不足；v3 要求先输出主题分组字段 `groups`，主要的合并 3 轮都能做到
- **JSON Schema 的字段顺序**：Spring AI 生成的 Schema 按字段名的字母顺序排列，而不是按 record 中的声明顺序。`groups` 能排在 `knowledgePoints` 前面，是因为 g 在 k 前面
- **示例题与样本题重叠**：最初打算用作示例的 HashMap、Spring 启动两组题都在样本里，模型照抄示例就能“做对”。改用样本以外的题（ConcurrentHashMap、类加载）作为示例
- **规则之间互相牵制**：v4 加入 4 条规则后修好了 3 处问题，但原来合格的细节知识点被主干代替了；v5 修正了其中一部分，大题的细节仍然常被主干代替。这个问题留到 #9
- **`deepseek-v4-pro` 超时**：超时设为 60 秒和 180 秒时各失败一次。把超时改成可配置（`WENGU_LLM_TIMEOUT`），原因未查，M0 改用 flash
- **一次返回正文为空**：结束原因是 STOP，计费了 3727 个输出 token，但正文为空，导致解析失败。原因未查实，疑似隐藏推理
- **开发环境**：Git Bash 中没有 JAVA_HOME，运行 Maven 时需要在 PowerShell 中临时设置

## 遗留问题

### 仍然开放的 issue

**#5 Scheduler 构造参数改为参数对象**

- **为什么存在**：`Scheduler` 的构造函数有 7 个位置参数，其中 `learningSteps` 和 `relearningSteps` 类型相同、位置相邻，写反了编译器发现不了；调用处的 `0.9`、`36500`、`true, null` 等字面量难以阅读。这是在 #1（PR #6）中记录的
- **为什么 M0 没做**：当时的调用方只有 `projectDefault()` 和测试，参数写反会被比对测试发现。issue 中约定：等 review 模块开始使用 `Scheduler`、需要按用户配置构造调度器时再处理
- **待决定**：issue 没有设置 milestone。需要决定是否归入 M1，以及是否和 M1 中“评分与调度”的工作一起做

**#9 改进知识点抽取的拆分粒度：大题细节被主干吞掉**

- **为什么存在**：v5 要求拆分大题时保留一个讲整体流程的主干。实际运行中，模型常常只输出主干，追问链里的细节不再单独输出。从模型的分组推理看，它会把样本中覆盖了部分追问的其他题当作这道大题的全部细节，没被覆盖的追问就被丢掉了。这是在 #4 中发现的
- **为什么 M0 没做**：M0 已经达标；v4、v5 显示，继续通过增加规则调整粒度，修好一处问题的同时会引出另一处问题。作者决定等 MVP 完成后，结合用户的真实修改数据再改进
- **待决定**：在 MVP 之后处理，没有设置 milestone

## 对 M1 的影响

- **M1 先做对话实验**：M0 的关卡只验证了“面试题文本 + `deepseek-flash`”的抽取。源码抽取、文档抽取、学习对话和评分建议都没有验证，所以 M1 先做学习对话与评分建议的 prompt 实验（#14），文档抽取在实现前也先做小规模实验（#26）
- **实验条件和产品条件差距很大**：M0 是 30 道题一次请求；产品中会有几百道题、增量导入，还可能使用 Ollama 的小模型。因此 M1 的抽取改为分批进行，并把已有知识点的标题作为上下文去重（#16）
- **#9 需要的数据没有地方保存**：#9 要用用户真实的修改数据改进抽取，但原数据模型只保存最终的知识点。M1 增加抽取草稿，保存模型的原始输出和 prompt 版本，并记录知识点的来源草稿（#15、#17）
- **骨架类工作今后也走 issue**：M0 中后端骨架等工作直接提交在 main 上，不属于任何 issue 或 PR，复盘中只能单独列出。今后这类工作同样先建 issue
