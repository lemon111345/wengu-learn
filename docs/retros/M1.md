## 遇到的问题

### 大模型与 prompt

- **超时设置不起作用，SDK 还会悄悄重试**（#16）：长资料切分时，同样的输入有时 60 秒失败、有时 183 秒失败。用 JDK `HttpServer` 写了一个假模型服务排查，查清两件事：
  - Spring AI 2.0.1 的 `OpenAiChatOptions` 没有设置超时时会填入 60 秒，覆盖客户端的配置，`spring.ai.openai.timeout` 等三个配置项都不起作用
  - SDK 默认自动重试 3 次，超时也会重发
  - 修法：每次请求都显式带上超时，并把 `max-retries` 设为 0；`LlmServiceTimeoutTest` 检查实际生效的超时和请求次数
  - M0 中“超时设为 180 秒仍然失败”这一条，当时设置的 180 秒其实没有生效，每次请求都是 60 秒（决策 005 的修订）
- **计费的 token 数波动大**（#15）：同一样本、输出内容相同时，计费的输出 token 能差好几倍（476 和 2282），和 M0 中“疑似隐藏推理”的现象一致（决策 011）
- **空正文**（#27）：流式调用正常结束却一个字都没有时，SDK 不报错；同步调用的空正文会被当成 JSON 解析失败去重试。改为在 `LlmService` 中主动判断，空正文不重试（决策 032）
- **Ollama 的 404**（#27）：模型名写错和模型还没下载都返回 404，提示补上了“或者还没有下载”
- **问过的问题只取最后一句不够**（#21）：老师常常连着问两句，只取最后一句时只剩“为什么？”，改为同一行中紧挨着的问句一起取
- **完整作答针对的对象**（#14）：v2 起初让学生回答来源题，而来源题可能比知识点宽，改为针对知识点标题中的问题
- **模型用表格画时间线**（#23）：真实对话中模型用表格画线程交错的时间线，渲染器补上了表格

### 后端

- **启动事件强制创建 bean**（#16）：重启处理用的是 `@EventListener(ApplicationReadyEvent)`，不受懒加载影响，不连数据库的实验入口也会创建它，导致全部实验入口启动失败。拆成 `ExtractionRecovery`，加了开关
- **事务提交前提交后台任务**（#16）：后台线程可能读不到刚插入的批次，改为事务提交之后再提交任务（决策 013）
- **Testcontainers 容器过多**（#19）：每种 `@MockitoBean` 组合各启动一个容器，缓存的上下文不关闭，整套测试会失败。改为共用一个静态容器
- **CSRF 令牌是延迟生成的**（#46）：GET 请求不会写 `XSRF-TOKEN` Cookie，前端的第一个 POST（登录）就被拒。加了一个过滤器，每个请求都读一下令牌（决策 022）
- **后台线程读不到当前用户**（#46）：`SourceService`、`ExtractionDraftService` 原来在 Service 内部调用 `CurrentUser`，抽取的后台线程和 SSE 的异步线程读不到。改为 Service 只接收 userId
- **MVC 异步请求的默认超时约 30 秒**（#19）：会切断较长的流式回复，改为 10 分钟
- **MyBatis-Plus 的 `updateById` 跳过 null 字段**（#20）：要把 `card_state.step` 改成 null 时，得用 `LambdaUpdateWrapper` 显式 set
- **评分写库后才读设置**（#20）：读设置出错时，评分已经存进库，前端却看到失败。改为先读设置再评分
- **JSON 列的处理器**（#15）：MyBatis-Plus 自带的 JSON 处理器基于 Jackson 2，项目用的是 Jackson 3，来源题号改存为 `"1,3,5"` 字符串（决策 012）
- **JSON Schema 的字段顺序**（#15、#16）：字段顺序用 `@JsonPropertyOrder` 固定，实测有效（决策 011、014）

### 前端与部署

- **TypeScript 7 不能用**（#47）：vue-tsc 依赖 TS 5、6 的 JS 接口，固定为 6.0（决策 023）
- **scoped 样式作用不到下拉菜单项**（#47）：菜单项由 Element Plus 的内部组件渲染，“退出登录”没有显示警示色，改为全局类 `wg-danger`
- **Nginx 默认缓冲会让 SSE 的回复攒到最后才出现**（#24、#26）：`/api/` 关闭缓冲，读超时 600 秒；请求体超过上限时，原来前端只能显示“服务暂时不可用”，改为用 `error_page 413` 返回统一格式的 JSON（决策 036）

### 开发环境与协作

- **反斜杠被吃掉**：用 heredoc 写 Java 正则时少了一个反斜杠，变成 Java 15+ 的合法转义 `"\s"`，能编译但行为错了。改为用编辑工具写含反斜杠的代码
- **编码**：PowerShell 5.1 的 `Set-Content -Encoding utf8` 会写 BOM，javac 报错；`Invoke-RestMethod` 会把中文响应解码成乱码；往 MySQL 灌中文时不加 `--default-character-set=utf8mb4` 会乱码
- **`git add` 的路径中有一个不存在时，整条命令失败**（#52）：错误被吞掉后，提交里只剩一个删除
- **无头浏览器验证**：没装浏览器扩展，页面验证用无头 Chrome 加 DevTools 协议。踩过的坑有：按 Enter 不提交登录表单；`dispatchKeyEvent` 要带 `text`；Windows 上 `execSync` 经过 cmd.exe 时，命令中换行之后的内容会被丢掉
- **CLAUDE.md 的 `@` 导入从未生效**（#75）：验证 #28 时用 `/context` 发现的
- **切到旧分支时工作区的 CLAUDE.md 会消失**（#28 之后）：#74 合并之前分出的分支里没有这个文件
- **推送时偶发 TLS 握手失败**：重试后成功
- **后端重启后要重新登录**：登录状态存在内存中（决策 022），自用时每次重启后端都要重新登录

## 经验教训

### 继续保持的

- **界面先在画布上定稿，再一次性交接**：10-30～11-01 用三天在画布上定下页面和交互，#44 把 ui.md、截图、画布源码一起交进仓库。之后前端的 6 个 issue 两天内完成，实现中没有因为界面返工。M2 中有界面的功能照此先设计再实现
- **用最小复现查问题**：超时问题靠 JDK `HttpServer` 写的假模型服务查清，并用 `LlmServiceTimeoutTest` 防止回退，比在真实模型上反复试更快、结论更可靠
- **先实验再实现**：#14 的对话实验发现“听懂和能讲出来是两回事”，学习流程因此加入完整作答；文档导入前的实验发现讲解型资料里没有现成的题目（决策 037）。这两处如果直接实现，做出来的功能都不好用
- **尽早开始自用**：11-02 达到“开始自用”线，三天的自用产出了 #77、#81、#82、#84，四个都是设计阶段没想到的

### 需要改的

1. **工期按写代码的时间估，但写代码不是瓶颈。** 估计 5～6 周，实际 11 天。估计时把“前端从零学起”当作最大的成本，而代码由 Claude Code 写，真正花时间的是做决定、审方案和真实使用。M2 起不按周估工作量：依赖使用数据的事（评分准确度、第二次复习、候选知识点）按“攒够多少次使用”来排
2. **建造挤占了使用，愿景跑在验证前面。** 截至 11-05，知识库有 226 个知识点，评分只有 10 次（复习 1 次），接着问 2 次；11-02 到 11-06 没有一天完成当天的全部任务，按决策 020 的口径，“连续自用 14 天”还没开始计数。M1 末等着使用数据的问题都缺数据，候选知识点因此移出 M1。同一时期，部署、多端、技能体系、Agent 的讨论产生了决策 033、034，想法池和“上线前必须完成”也变长了。M2 的头等任务是使用本身
3. **Must 要按 PRD 自己的标准来定。** PRD 的判断标准是“没有它，闭环还能跑通吗”。接着问和候选知识点是作者在 #14 实验中扮演学生时加进 M1 Must 的（决策 008），按这个标准都不是 Must。自用中接着问只用了 2 次，候选知识点还没做。新功能进 Must 之前，先在自用中确认确实需要
4. **待办散落在太多地方。** 附录二从 PRD、决策的遗留问题、issue、本地笔记和对话中汇总出一百三十多条，有重复，也有已解决却没删的。决策中的“遗留问题”适合记录当时的取舍，不适合当待办清单。M2 开始时逐条定去向：建 issue、进想法池，或者写明不处理后关掉。以后待办只放在 issue 中
5. **先确认条件真的生效，再下结论。** M0 中“超时设为 180 秒仍然失败”的结论，建立在一个没有生效的配置上；CLAUDE.md 的 `@` 导入一直没生效，也一直没人发现。用实验结果或配置做判断前，先确认它真的在起作用：打日志、用 `/context` 查看、在测试中断言实际生效的值
6. **规则太宽就会被绕开。** M0 约定“骨架类工作也先建 issue”，M1 中有 4 个 PR 没有对应的 issue，理由都说得通。规则改为：只改文档的 PR 可以不建 issue，但要在 PR 描述中写明原因
