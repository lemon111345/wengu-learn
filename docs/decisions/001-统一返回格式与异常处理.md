# 001 统一返回格式与异常处理

## 背景

后端所有接口需要统一的返回格式，前端才能用一套逻辑处理成功和失败；异常也需要集中处理，避免每个 Controller 各写一遍 try-catch，同时防止内部错误信息（堆栈、SQL、请求参数里的 API Key）泄露给前端。

## 决策

1. 响应体统一为 `Result<T>(code, message, data)`，用 Java record 实现。
2. **HTTP 状态码表达真实结果**（200 / 400 / 404 / 405 / 500），body 里的 `code` 给出更细的原因。
3. `code` 是字符串，直接取 `ErrorCode` 枚举名（如 `"NOT_FOUND"`），`ErrorCode` 同时绑定 HTTP 状态码和默认提示。
4. 业务代码通过抛 `BusinessException(ErrorCode, message)` 表达可预期的失败。
5. `@RestControllerAdvice` 的 `GlobalExceptionHandler` 统一转换异常：
   - 业务异常：按 ErrorCode 返回，记 warn 日志，不打堆栈
   - 框架抛出的参数错误、路径不存在、方法不支持：转成 400 / 404 / 405，不记日志
   - 其他异常：返回 500 和通用提示，记 error 日志和完整堆栈，**不把异常消息返回前端**
6. Controller 显式声明返回 `Result<T>`。

## 理由

- 状态码保持真实，Nginx 日志、浏览器开发者工具、前端 axios 的错误拦截都能正常工作。
- 字符串 code 读日志和前端代码时一眼看懂，不用查数字对照表。
- 显式返回 `Result<T>`，读代码就能看到真实的响应结构，没有隐藏的包装逻辑。
- 兜底异常不回传消息，配合“API Key 不得出现在日志中、只显示末四位”的约束，降低信息泄露风险。

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 永远返回 HTTP 200，只靠 body 里的 code 区分成败 | 让 HTTP 层的监控、日志和前端错误拦截全部失效 |
| 数字 code（如 40401） | 需要查表才能看懂，没有实际好处 |
| `ResponseBodyAdvice` 自动包装返回值 | 是“魔法”，看不出真实返回类型；String 返回值和 SSE 流式接口都要特殊排除 |
| Spring 自带的 `ProblemDetail`（RFC 9457） | 只规范错误响应，成功响应仍是另一种结构，前端要处理两套格式 |
| `code` 与枚举名分开存（单独的字段） | 现在没有需要两者不同的场景，多一个字段就多一处可能写错；代价是枚举改名即改接口，已在 ErrorCode 注释中提醒 |
