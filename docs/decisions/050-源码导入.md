# 050 源码导入：选文件、存储和抽取

## 背景

#90 的第一步：用户导入自己项目的源码，抽出个人经历类知识点，确认后进入知识库。决策 048 根据 #89 的实验定了方向：
- 用户勾选文件，限制总大小；
- 抽取用 v2，再加上得分点；
- 保存文件快照。

这里定具体做法。学习和复习是 #90 后面两步的事，不在这里。

决策 049 留给 M3 的默认卡组，所以这份用 050。

## 决策

### 1. 在浏览器里选项目文件夹，前端读出文字再发给后端

- 导入页新增“源码”方式。用户选择一个文件夹（`<input webkitdirectory>`），前端列出文件树，用户勾选文件。
- 前端读出勾选文件的文字，以 JSON 发给后端。不上传 zip，也不上传二进制文件。
- 文件树里不显示的：
  - 名字以 `.` 开头的目录；
  - `node_modules`、`target`、`build`、`dist`、`out`、`bin`、`obj`、`vendor`、`__pycache__`；
  - 不认识的扩展名。
- 默认勾选：常见源码扩展名（`java`、`kt`、`go`、`py`、`js`、`ts`、`vue`、`jsx`、`tsx`、`cs`、`c`、`cpp`、`h`、`rs`、`php`、`rb`、`scala`）。
- 显示但默认不勾：
  - 配置和其他文本（`xml`、`yml`、`yaml`、`properties`、`json`、`sql`、`md`）：配置文件里可能有密码和密钥；
  - 路径里有 `dto`、`entity`、`mapper`、`model`、`test`、`tests` 的目录：实验里去掉前三类省约 20% token，抽出的主题基本不变；测试代码一般不是面试要讲的内容。
- 文件的具体规则，比如扩展名清单，放在前端：后端只校验大小和格式。

### 2. 总大小上限 15 万字符，前后端都检查

- 实验里 14.5 万字符（含 prompt 约 4.8 万 token）DeepSeek 一次处理完，约 1 分钟。
- 后端不知道用户把上下文设成了多少（决策 045），所以用固定上限，不按模型动态算。本机小模型放不下时，靠决策 045 的截断检测给出明确提示。
- 其他限制：最多 300 个文件，路径不超过 500 字符，路径不能重复，文件内容不能为空。超出时返回 400，并附上处理建议。

### 3. 文件内容存进新表 `source_file`

- `source` 新增类型 `CODE`。
  - `content` 存文件清单，一行一个路径；
  - `questions` 为空。
- `source_file`：`id`、`user_id`、`source_id`、`path`、`content`、`chars`、`file_order`。导入后不再修改，就是决策 048 的“文件快照”。
- 归 source 模块管理。knowledge 和以后的 chat 都通过 `SourceService` 按 source 和路径取文件。chat 不依赖 source，学习时由 knowledge 把依据文件放进学习材料里（`StudyMaterial`）。

### 4. 得分点写进要点里，作为每条核心要点下面的小项

```
1. 已有建议就直接返回，不再调用模型
   - 查到已存在的建议时直接返回
   - 不重复调用模型，也不覆盖之前的结果
2. ……
```

- 要点 `summary` 仍是一段文字：1～4 条核心要点，每条下面 2～3 个得分点。
- 学习、复习、评分的 prompt 都直接读这段文字。
- 用户在知识库里改要点时，得分点跟着一起改，“恢复 AI 版本”也照常可用。

### 5. 源码知识点特有的数据存进 `kp_code`

| 字段 | 内容 |
|---|---|
| `kp_id`（主键） | 知识点 |
| `user_id` | |
| `source_id` | 来自哪次导入 |
| `details` | 细节，0～3 条，漏了不降档 |
| `evidence` | 代码依据 JSON：`[{file, symbol}]` |
| `unverifiable` | 代码证明不了的问题 JSON：`["…"]` |
| `prerequisites` | 前置概念 JSON：`[{concept, explanation}]` |

- 草稿条目对应的表是 `extraction_draft_item_code`（主键 `item_id`），字段相同，但没有 `source_id`（草稿里已经有）。确认时，条目被接受的话复制一份到 `kp_code`。
- 题库里抽出的个人经历题没有这一行。

### 6. 抽取：沿用草稿、批次和确认的流程

- **接口**：`POST /api/sources/code` 只保存，不调用模型。前端拿到 sourceId 后，接着调用现有的 `POST /api/drafts` 发起抽取，所以抽取进度、失败重试和“等你确认”都不用另做。
- **只抽一批**：15 万字符以内一次调用就够。批次的 `questions` 列存 `[]`，输入就是这个 source 的全部文件。传了 `questionIds` 时返回 400。
- **prompt**：`code-extraction-v3`，在 v2 的基础上加上得分点：每条核心要点拆成 2～3 个得分点，合起来要覆盖这条要点的全部内容，包括其中的“为什么”和“之后怎样”。类型固定为 EXPERIENCE，不让模型选。
- **校验**：
  - 代码依据的文件必须在这次导入的文件里，symbol 的类名和方法名必须在文件里真实出现（把 #89 实验的校验搬进正式代码）；
  - 每条核心要点下面要有 2～3 个得分点；
  - 不通过就重试一次，和题目抽取一样。
- **不做去重**：同一个项目导入两次，会抽出重复的题。现有去重是按题目和已有知识点的标题判断的，不适用于源码。
- **草稿接口**：条目多一个 `evidence` 字段，确认页用它显示“依据”；其他材料的条目这个字段为 null，接口只增不改（决策 034）。
- **确认**：和现有流程一样生成知识点、关联材料。个人经历类在这一步仍然“只收录”，不初始化 card_state；#90 的第二步放开以后，再给已有的个人经历知识点补上。

## 理由

- **浏览器选文件夹**：用户能看到并决定发出去的是哪些文件，配置文件默认不勾，避免把密钥发给模型。
- **文件单独成表**：学习时每轮只要取两三个依据文件，按路径查就行，不用每次读出整个项目。
- **得分点放在要点里**：改要点时得分点不会过时，也不用为它另做编辑界面。
- **特有数据放侧表**：大部分知识点用不到这些字段。M3 的默认卡组也要给 `knowledge_point` 加列，各加各的，冲突更少。
- **复用草稿流程**：抽取要 1 分钟左右，现有流程已经处理了异步、失败重试、离开后回来确认这些情况。

## 放弃的方案

- **上传 zip**：后端要解压，还要处理二进制和编码；用户看不到自己选了哪些文件，配置文件里的密钥容易一起发出去
- **粘贴 GitHub 仓库链接**：#90 明确不做
- **把全部文件拼成 JSON 存进 `source.content`**：每轮对话都要读出整个项目，再从中挑出依据文件
- **得分点单独存一列**：结构更清楚，但用户改要点时得分点会过时，要么另做编辑界面，要么每次修改都重新调用模型
- **源码字段加在 `knowledge_point` 上**：大部分知识点用不到，和 M3 的改动挤在同一张表上
- **按模型上下文动态算上限**：后端拿不到用户设置的上下文长度

## 遗留问题

- 同一个项目重复导入的去重，等自用中遇到再定
- 代码依据只校验了类和方法存在，不校验要点和代码一致。注释少的项目错误更多（决策 048），导入页会提示用户
- 题库抽出的个人经历题没有源码，放开“只收录”后怎么学，在 #90 的第二步定
- 文件快照不随用户的代码更新，要更新就重新导入
