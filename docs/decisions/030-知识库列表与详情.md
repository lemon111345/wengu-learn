# 030 知识库列表与详情

## 背景

#50 给知识库页面（ui.md 5.9）提供列表和详情两个接口，前端在 #51。编辑、暂停、删除、合并已经在 #25 做完（决策 029），操作都不返回数据，前端操作完重新取列表或详情。要定的是：

- 掌握程度怎么判断，几种情况同时成立时算哪一种
- 按掌握程度、下次复习排序时，没有稳定性或不会复习的知识点放在哪里
- 下次复习和学习记录的日期要换算成学习日，knowledge 读不到用户设置
- 是否分页，是否返回各类型的数量
- 合并过来的学习记录、来源题号怎么取

## 决策

### 1. 掌握程度（`Mastery`）

按先后顺序判断，阈值写成常量：

| 顺序 | 条件 | 掌握程度 |
| --- | --- | --- |
| 1 | 类型不参与调度（M1 的系统设计、个人经历） | 只收录 RECORD_ONLY |
| 2 | 暂停 | 暂停 SUSPENDED |
| 3 | 没有 card_state，或 last_review 为空 | 待学 NEW |
| 4 | 稳定性 ≥ 21 天 / [7, 21) / [2, 7) / < 2 天 | 牢固 SOLID / 熟悉 FAMILIAR / 一般 FAIR / 生疏 SHAKY |

- **只收录排在暂停前面**：这个类型本来就学不了，暂不暂停都一样。从别的类型改过来的保留了 card_state（决策 029），这里也不看
- 判断是一个纯函数 `Mastery.of(type, status, card)`，边界和先后顺序有单元测试
- 以后的技能亮度（决策 033，规划中）有意使用可提取率，和这里的掌握程度用途不同、并存，区别见决策 033 第 6 节

### 2. 列表 `GET /api/knowledge-points`

- 参数：`mastery`、`type` 各选一个，不传表示全部；`sort` 为 ORDER（默认）、MASTERY、NEXT_REVIEW；`direction` 为 ASC（默认）、DESC。值不合法时 400
- 返回 `{total, counts, items}`：
  - total 是全部没删除的知识点数（“共 Y 个”）
  - counts 是七种掌握程度的数量，**只受类型筛选影响**，不受掌握程度筛选影响：按钮上显示的是切过去能看到几个
  - items 两种筛选都生效：`{id, title, type, mastery, nextReview}`
- **不分页**：MVP 只有几百个知识点，各档数量本来就要全部算一遍
- **不返回各类型的数量**：ui.md 的类型下拉框没有数字，要的时候再加
- 全部在内存中处理：先按学习顺序取出，判断掌握程度，按类型筛选后统计，再按掌握程度筛选、排序。和每日计划的取舍一样（决策 002）

### 3. 排序

- ORDER：学习顺序（sort_order、id），不分方向
- MASTERY 按稳定性，ASC 是生疏的在前；NEXT_REVIEW 按到期时间，ASC 是早的在前
- 两种排序下，**待学、暂停、只收录总在学过的后面**，依次是待学、暂停、只收录，组内保持学习顺序；方向只影响学过的那些。它们没有稳定性，或者不会复习，放进中间没有意义
- 稳定性或到期时间相同时保持学习顺序（排序是稳定的）

### 4. 下次复习

- `nextReview: {date, days}`：date 是学习日，days 是距今天几个学习日，和评分预览的格式一致。days 为 1 是明天（ui.md 用 `--wg-warn`）；0 或负数是已经到期，在今天的计划里
- **只有学过的四档才有**，待学、暂停、只收录为 null。暂停的虽然有到期时间，但暂停期间不会复习，显示出来会让人以为那天要复习

### 5. 详情 `GET /api/knowledge-points/{id}`

返回 `{id, title, type, status, mastery, nextReview, summary, aiSummary, summaryEdited, reviews, sources}`：

- **status**：暂停按钮显示“暂停复习”还是“恢复复习”看它。只收录的类型也能被暂停，mastery 表达不了
- **aiSummary、summaryEdited**：AI 原文来自确认时关联的草稿条目（确认时不能编辑条目，所以条目就是 AI 写的），和当前要点去掉首尾空白后比较。不是从草稿来的知识点 aiSummary 为 null、summaryEdited 为 false。“恢复 AI 版本”时前端把 aiSummary 填回编辑框，走 PATCH（决策 029）
- **reviews**：`[{date, firstReview, rating, ratingAi, mergedFrom}]`，最近的在前。包括 merged_into 指向它的知识点的记录，mergedFrom 是被合并的知识点的标题，自己的为 null。merged_into 始终指向还在的知识点（决策 029），只查一层
- **sources**：`[{sourceId, name, questionIds}]`，来自 kp_source，按材料 id（导入顺序）排列。题号来自自己和被合并的知识点的草稿条目，按条目所在草稿的材料归到对应的来源下
- 不存在、不属于当前用户、已删除（包括被合并的）404

### 6. 新增依赖 knowledge → user

下次复习和学习记录的日期要换算成学习日，要读用户的时区和 day_start_hour。user 是叶子模块，加这一条不会产生环，理由和 chat → user（决策 026）一样。换算仍用 common 的 `StudyDay`。决策 002 同步修订。

### 7. 放在新的 `KnowledgeLibraryService`

列表和详情只读，放在 knowledge 中新建的 `KnowledgeLibraryService`，修改仍在 `KnowledgePointService`。KnowledgePointService 已经四百行左右，再加组装详情的代码会很难读。两个类都显式排除删除的知识点（决策 029）。

## 理由

- **掌握程度的先后顺序**：先看“能不能学”（类型），再看“要不要学”（暂停），最后看“学得怎么样”，每一步都比后一步更根本
- **排序时把待学等放在最后**：用户点“掌握”是想看学过的哪些牢、哪些不牢，没学过的混在中间是噪音
- **数量只随类型变**：按钮上的数字是“切过去能看到几个”，掌握程度筛选生效时其他按钮的数字不能变成 0
- **学习记录按 merged_into 查**：决策 029 不搬学习记录，显示时一起取，历史数据保持原样

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 列表和详情放在 plan（plan 已经依赖 user） | 知识库不属于每日计划，职责不对 |
| 返回 UTC 时间，前端自己换算学习日 | 违反“前端日期一律用接口返回的学习日”；前端还要处理夏令时 |
| 暂停排在只收录前面 | 只收录的类型本来就学不了，暂停它不改变什么，标成“暂停”反而让人以为恢复后就能学 |
| 待学等按方向一起反转（DESC 时排在最前） | 用户点“掌握”是想看学过的，反向后前面一屏都是待学 |
| 暂停的也显示下次复习 | 暂停期间不会复习，日期会误导 |
| offset 分页 | 几百条数据量很小，而且各档数量要全量统计 |
| 列表和详情加进 KnowledgePointService | 那个类已经很长，读写混在一起 |
| 去重时补关联的材料（决策 014 的 covered）也显示题号 | 要解析批次的 covered JSON，暂时只显示材料名 |
