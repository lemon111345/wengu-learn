# 051 带源码的个人经历题参与调度

## 背景

决策 007 定下：个人经历类知识点要结合用户源码追问，M1 只收录、不进每日计划。#90 已经做完源码导入（决策 050），学习对话也能带上源码了（#124），这一步要让个人经历题能学，修订决策 007。

个人经历题有两个来源：

- **源码导入**：有 `kp_code`，学习时老师能看到依据的代码
- **题库抽出**：比如“你项目里限流是怎么做的”，没有源码。2026-11-19 作者的开发库里一共 20 道个人经历题，19 道来自源码，1 道来自题库；朋友导入题库时，这类题会更多

要定的是：没有源码的个人经历题怎么办。

## 决策

### 1. 只有带源码的个人经历题参与调度，题库抽出的仍然只收录

一个知识点参与调度（进每日计划、能开始学习、掌握程度不是“只收录”），当且仅当：

- 类型本身参与调度（`KnowledgePointType.isScheduled()`），或者
- 是个人经历题，而且有 `kp_code`（`isScheduled(boolean hasCode)`）

改动的地方：

- 确认草稿时，带源码的个人经历题当场初始化调度状态
- 每日计划的两条查询（`activeInOrder`、`pendingInOrder`）用子查询判断 `kp_code`
- 改类型时，改成个人经历的知识点带源码，就补上调度状态
- 开始学习按 `isScheduled(有没有源码)` 判断
- 掌握程度 `Mastery.of` 的参数从类型改成“是否参与调度”，知识库列表多查一次这个用户哪些知识点带源码

### 2. 迁移 V18 给已经确认的带源码个人经历题补上调度状态

已经确认的源码题没有 `card_state`，要补一行新卡，初始值和 `Card.newCard` 相同。

**这是一个例外**：迁移直接写 review 模块的 `card_state` 表，越过了“模块之间只调 Service”的规则（决策 002）。理由是这是一次性补数据，迁移只跑一次、最简单；规则要防的是业务代码之间的耦合，一次性的迁移不会被别的代码依赖。以后再有类似的补数据，也优先用迁移，在迁移文件和决策中写明例外。

### 3. 没有源码的个人经历题由 AI 帮忙梳理经历，留到以后的版本

这是 prd 想法池中的一条：老师引导用户讲出自己的经历（遇到什么问题、怎么选的、结果怎样），再把讲出来的内容整理成要点。它要另写一套对话和评分方式，工作量和 #89 差不多，不在 #90 里做。

## 理由

- 老师没有源码，就没有事实依据：只能泛泛地讲“这类题怎么答”，评分也没有标准，学了也不扎实
- 只收录不会丢东西：题库抽出的个人经历题照样在知识库里，以后有了梳理经历的学法，或者用户导入了相关源码，再学也不迟

## 放弃的方案

- **所有个人经历题都能学，没有源码的走普通学习对话**：改动最小，但老师手里只有一句标题，容易讲成空话
- **现在就做 AI 梳理经历**：工作量大，而且要先像 #89 那样做实验，会拖慢 #90
- **给带源码的个人经历题单独设一个类型**：类型表示“怎么问”，不表示“有没有材料”，再加一个类型会让知识库的类型筛选和统计变乱
- **用启动时运行的 Java 代码补调度状态**（调用 `ReviewService.ensureCard`）：守住了模块边界，但每次启动都会执行一段实际上只需要跑一次的代码

## 遗留问题

- 源码题和题库题讲的是同一件事时（比如题库里有“你项目里怎么做限流”，源码里也抽出了限流），不会自动合并，用户可以在知识库里手动合并
