# 024 今天页的补充数据

## 背景

今天页（ui.md 5.2）除了待复习、待新学，还要显示：今天已完成的条目和评分、进度、今天已学的分钟数、接下来 7 天每天要复习的数量、“等你确认”的草稿。决策 016 当时只返回了今天已学的新知识数，说“页面需要显示已完成时再加”。#48 补上这些数据，要定几条口径：

- 已完成的知识点被暂停或删除后是否还显示
- 7 天是否包括今天；已经过期没复习的算在哪一天
- 草稿列表要不要分页，已确认的草稿留多久
- 今天已学的分钟数现在没有数据来源（会话的有效时长由 #19 添加）

## 决策

### 1. 今天已完成的条目放在 `GET /api/plan/today` 的 `completed` 中

- 来自今天学习日 `[start, end)` 内的 review_log，每条带今天的评分和是否新学，按完成时间排列。前端按 `firstReview` 放进“新学”或“复习”列表
- 同一个知识点今天评了多次时取最后一次，位置也跟着最后一次走。现在没有学习步，一天内一般不会再到期，这只是防一手
- **暂停的仍然显示，删除的不显示**。“今天学过”是已经发生的事，暂停不改变它；删除是用户不想再看到这个知识点。软删除由 #25 添加，那时在 knowledge 的查询中排除
- 进度 = 已完成 ÷（已完成 + 待复习 + 待新学）
- review 返回评分流水（`ReviewRecord`），knowledge 按 id 查标题和类型（`summaries`，不排除暂停的），plan 组合，各自只读自己的表（决策 002）

### 2. 接下来 7 天放在 `GET /api/plan/today` 的 `upcomingReviews` 中

- **从明天起数 7 个学习日，不含今天**。今天到期的、已经过期还没复习的，都已经在今天的复习列表里，不重复算。设计稿也是从明天画起
- 每一天按用户的时区和 day_start_hour 划分，和“今天”同一个算法（`StudyDay.ofDate`）。夏令时开始、结束的那一天是 23 或 25 小时
- 只算复习过的卡，新卡不算；暂停的不算：review 给出 `(kpId, due)`，knowledge 过滤掉暂停的，plan 按学习日分组
- 不另开接口：今天页一次请求拿到全部数据，用的是同一个“现在”；评分后两部分都要刷新

### 3. 今天已学的分钟数这次不加

会话的有效时长由 #19 添加，现在加只能固定返回 0，前端会显示“今天已学 0 分钟”这样的假数据。由 #19 在 `GET /api/plan/today` 中加上，#49 在没有这个字段时不显示这半句。

### 4. 草稿列表 `GET /api/drafts`

- 返回**全部未确认的草稿和最近 10 份已确认的**，新的在前，不分页
- 每一项带 `itemCount`：成功批次中的条目数，和详情中 items 的个数一致，确认后不变
- 草稿列表接口在 `feat/22-frontend-import` 上先写好（当时返回最近 20 份），这次 cherry-pick 过来再修改
- 候选知识点的草稿（#31）还不存在，由 #31 加进这个列表

## 理由

- **未确认的不限数量**：只取最近 N 份时，一份旧的“等你确认”会被新导入的挤出列表，今天页的提示就再也看不到它。未确认的草稿通常只有几份，全部返回没有负担。已确认的只用于导入页的“最近导入”，几份就够
- **已完成的数据从流水取**：card_state 只有“现在”，评分后 due 已经推到未来，看不出今天评过什么

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 草稿列表只返回最近 20 份（`feat/22-frontend-import` 上的写法） | 旧的未确认草稿会被挤出列表 |
| 草稿列表分页 | M1 的草稿很少，分页让今天页和导入页都更复杂 |
| 7 天包括今天 | 今天的复习已经在列表里，柱子再算一遍会重复；过期的也要另想放在哪一天 |
| 7 天、草稿列表另开接口 | 今天页要多发请求，几次请求之间的“现在”可能不同 |
| 已完成的条目排除暂停的 | 今天确实学过；进度会因为暂停而倒退 |
| 分钟数先返回 0 | 是假数据，用户会以为计时坏了 |

## 遗留问题

- 已完成的条目只看 review_log。#20 写入流水后，“评分后立刻显示下次见”（乐观更新）与计划刷新之间可能有短暂不一致，由前端处理
- 草稿目前没有“丢弃”操作，失败后不再处理的草稿会一直留在列表中。需要时再加
