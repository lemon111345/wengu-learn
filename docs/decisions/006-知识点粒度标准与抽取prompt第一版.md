# 006 知识点粒度标准与抽取 prompt 第一版

## 背景

知识点是 FSRS 调度的最小单位，每个知识点对应一张复习卡。粒度太粗，一张卡里有两件事，记住一件、忘了一件时无法评分；粒度太细，每天的复习量变大，内容也变得零碎。技术方案中的粒度标准是基于 200 道题的分析写的初稿，M0 需要用真实抽取结果和人工标注来验证（issue #4）。

抽取的实现方式（一次请求、结构化输出、temperature、分组字段）见 [决策 005](./005-知识点抽取实现.md)。

## 实验设置

- 样本：30 道 Java 后端面试题，来自私人题库，只放在 `data-private/`，本记录不引用原文
- 模型：DeepSeek `deepseek-flash`，temperature 0.2
- prompt：v1～v5，存放在 `backend/src/main/resources/prompts/`。v1～v3 用于调通拆分与合并（#3），v4、v5 根据人工标注调整（本 issue）
- 标注对象：v3 的一轮结果，34 个知识点，由作者审核标注

## 统计结果

| 标注 | 数量 |
| --- | --- |
| 合格 | 31 |
| 需修改 | 3 |
| 应删除 | 0 |
| 遗漏 | 1 |

修改率 =（需修改 + 应删除 + 遗漏）÷ 34 ≈ **12%**。

按类型：

| 类型 | 数量 | 有问题的 |
| --- | --- | --- |
| MECHANISM 原理机制 | 17 | 3 |
| CONCEPT 原子概念 | 7 | 0 |
| ENUMERATION 列举 | 4 | 0 |
| COMPARISON 对比 | 2 | 0 |
| TROUBLESHOOTING 排查实战 | 2 | 0 |
| SYSTEM_DESIGN 系统设计 | 2 | 0 |
| EXPERIENCE 个人经历 | 1 | 0 |

没有一处标注指出类型判断错误，类型准确度为 34/34。3 处需修改都是粒度和范围问题，不是类型问题。样本量小，个人经历只有 1 个，对比、排查、系统设计各 2 个，这几类的结论只作参考。

## 主要问题

1. **摘要越界**：一个“扩容机制”的知识点，摘要写进了属于另一条追问（线程安全）的内容
2. **“是什么”过于单薄**：一道问“什么是 X”的题一两句话就能答完，单独成卡没有意义，应该并入以它为前提的“如何解决 X”那道题
3. **超出原题限定的角度**：一道“从网络角度”提问的题，拆出的知识点写进了页面渲染
4. **缺少主干**：一道流程类大题拆成了几个细节，但没有一个讲整体流程的知识点。面试官通常先问整体，再追问细节

另外，对“Spring refresh 流程”和“Spring Boot 启动流程”这一组，作者的结论是不合并：后者包含前者，但面试中是两个问题。这推翻了技术方案初稿中把它当作合并例子的写法。

## 决策

### 1. 粒度标准

在初稿“一个知识点 = 能在 3～5 分钟对话里讲清、用一个问题就能检验的概念”的基础上，规则定为：

- **拆分**：原理类大题按追问链拆成多个知识点，其中必须有一个讲整体流程的主干，排在细节之前；主干是另加的，不代替细节
- **合并**：问法不同、考的是同一内容的题，合并为一个知识点
- **小追问不拆**：“是什么”加上一两句就能答完的直接追问，合为一个知识点；追问本身是完整机制时才拆开。这条也适用于不同的题：一两句就能答完的“是什么”题，并入以它为前提的那道题；两道题各自都要讲几分钟的，即使相关也不合并
- **摘要不越界**：摘要只覆盖原题和它的直接追问；原题限定了角度的，不讲角度之外的内容
- **包含不算重复**：一个流程包含另一个流程时不合并，分别输出，先排作为基础的那个
- **排序**：先基础概念，后原理机制，再综合应用；同一主题的知识点排在一起
- 系统设计题和个人经历题各自作为一个整体，不拆分

### 2. 抽取 prompt 第一版定为 v5

v5 = v3 + 上述规则。规则是在 v4 中加入的，v5 修正了 v4 的两处副作用。各版本 3 轮的对比：

| 检查项 | v4 | v5 |
| --- | --- | --- |
| 摘要越界（问题 1） | 3/3 修好 | 3/3 修好 |
| “是什么”并入（问题 2） | 0/3 | 3/3 修好 |
| 超出限定角度（问题 3） | 3/3 修好 | 2/3 修好 |
| 补上主干（问题 4） | 3/3 | 3/3 |
| 原来合格的“有哪些”和“为什么选这个”两题保持分开 | 1/3，其余两轮被误合并 | 3/3 |
| 大题的细节知识点保留 | 基本被主干代替 | 仍常被代替，见下文 |

v5 的修改率**是估算的，没有经过作者重新标注**：按本次标注的标准对照 v5 的 3 轮结果，估计在 10%～20% 之间。M0 是否达标，以 v3 的实测 12% 为准。

### 3. 已知问题：大题细节被主干吞掉

v5 中，原理类大题常常只输出主干，追问链里的细节不再单独输出。从分组推理看，模型会把样本中覆盖了部分追问的其他题当作这道大题的全部细节，没被覆盖的追问就丢掉了；几条“少拆”方向的规则也比“细节照常输出”这一句更强势。

这个问题会让用户在 MVP 中手动补充知识点，但不影响 M0 的结论。作者决定等 MVP 完成后再改进，记录在 #9。

## 结论

对照 PRD 的验收标准“人工修改不超过三成”：**达标**（v3 实测约 12%）。M0 的知识点抽取验证完成，可以进入 M1。

## 理由

- **选 v5 而不是 v3**：v3 有实测数字，但标注出的 4 处问题都没修；v5 落实了作者确认的粒度标准，代价是细节偏少，这一点有明确的改进方向
- **包含关系不合并**：面试中“整体流程”和“其中一步”确实是两个问题，合并后一张卡要讲的内容太多，评分会变得含糊
- **M0 不再继续调 prompt**：v4、v5 说明靠增加规则来调粒度，已经到了修好一处、坏掉另一处的阶段。等 MVP 中积累了用户真实的修改数据，再据此调整更有效

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 第一版选 v3 | 标注出的 4 处问题都没修 |
| 第一版选 v4 | 细节被主干代替，还误合并了原本合格的两道题 |
| 包含关系也算重复、合并 | 一张卡的内容过多，评分含糊；规则也会误伤其他题 |
| 示例直接使用样本题 | 模型照抄示例就能“做对”，实验测不出真实效果 |
| M0 中继续出 v6 | 收益递减；M0 已达标，改进放到 #9 |
| 重新标注 v5 得到实测修改率 | M0 结论用 v3 的实测数据已经可以得出 |
