# 015 确认草稿

## 背景

#17：抽取结果先存成草稿（决策 012），用户看过、取消勾选不要的条目之后，才生成知识点并进入每日计划。确认要同时写好几张表：知识点、知识点与材料的关联、调度状态、条目的处理结果、草稿的确认时间，其中调度状态归 review 模块管理。要求是：要么全部写入，要么都不写；review 不能依赖 knowledge；被取消的条目也要记下来，供 #9 对比 AI 输出和最终结果。

## 决策

### 1. 接口：传取消勾选的条目

`POST /api/drafts/{id}/confirm { rejectedItemIds? }`，返回确认后的草稿。不传或为空时全部接受。

- 只有 READY（所有批次都成功）的草稿能确认，否则返回 409。有批次失败时先重试：如果允许确认，失败批次中的题会悄悄地没有被抽取，用户很难发现
- 已经确认过的草稿再确认、再重试，都返回 409
- rejectedItemIds 中有不属于这份草稿的 id，返回 400
- **全部取消勾选也可以确认**，等于“这份草稿处理完了，一个都不要”，取消的条目照样记录

### 2. 一个事务完成，先锁住草稿

`ExtractionDraftService.confirm` 在 `TransactionTemplate` 中：

1. `SELECT … FOR UPDATE` 锁住草稿，检查还没确认过、状态为 READY
2. 勾选的条目按草稿中的顺序（批号、批内顺序）交给 `KnowledgePointService.create`：
   - sort_order 接在该用户已有知识点的最大值之后，连续编号，新知识就按这个顺序派发（决策 009）
   - 每个知识点记下 `draft_item_id`，关联到这份材料（kp_source）
   - 参与调度的类型调用 `ReviewService.initCards` 初始化 card_state
3. covered 中引用的已有知识点（决策 014）也关联到这份材料，已经关联过的跳过。引用同一草稿中其他条目的不用另外处理：条目本身会生成知识点，关联的就是这份材料
4. 每个条目记下 ACCEPTED 或 REJECTED，草稿写入 confirmed_at

`KnowledgePointService` 和 `ReviewService` 是另外的类，在同一个线程中调用，会加入这个事务；任何一步失败都整体回滚。

### 3. 表结构（V6）

| 表 | 新增字段 | 说明 |
| --- | --- | --- |
| knowledge_point | `draft_item_id`（可为空，建索引） | 来自哪个条目，以后能逐条对比 AI 输出和最终结果（#9）。来源草稿通过条目可以查到，不重复存。合并（#25）或手动新建的知识点为空 |
| extraction_draft | `confirmed_at`（可为空） | 决策 013 约定“已确认”单独存，和由批次推算的状态分开。接口中 confirmed_at 不为空时 status 为 CONFIRMED |
| extraction_draft_item | `decision`：ACCEPTED / REJECTED（可为空） | 为空表示草稿还没确认 |

card_state、kp_source 在 V1 已经建好，不用改。

### 4. 哪些知识点参与调度，由 knowledge 决定

- `KnowledgePointType.isScheduled()`：SYSTEM_DESIGN、EXPERIENCE 返回 false（决策 007），这两种类型不传给 review
- `ReviewService.initCards(userId, kpIds)` 只接收 id，为每个 kp_id 写一张新卡：LEARNING、立即到期、last_review 为空（`Card.newCard`）。它不知道知识点是什么类型
- review 新增 `CardState` 实体（主键是 kp_id，由调用方给定）和 `CardStateMapper`

### 5. 用源码扫描检查 review 的依赖

`ReviewDependencyTest` 扫描 review 包下的源码，凡是引用了 `com.wengu.` 下除 review、common 以外的包都算违规（决策 002：review 不依赖其他业务模块）。不为此引入 ArchUnit。验证过：临时加一个引用 knowledge 的文件，测试会失败并指出文件名。

## 验证

- `DraftConfirmTest`（真实 MySQL，模型用模拟对象）：生成知识点的顺序和 sort_order（接在当前用户的最大值后面，不受其他用户影响）；SYSTEM_DESIGN 和 EXPERIENCE 没有 card_state；取消的条目记为 REJECTED、不生成知识点；covered 引用的已有知识点补上关联、不重复关联；`initCards` 抛异常时什么都没写入；全部取消；未完成、失败、重复确认、确认后重试、条目不属于草稿
- `ReviewServiceTest`：初始化后的字段；重复初始化同一个 kp_id 时整体失败
- 本地开发库 + 真实模型：确认 #16 端到端留下的草稿（26 个条目，取消 1 个），得到 25 个知识点、sort_order 1～25 连续、23 张新卡（SYSTEM_DESIGN 和 EXPERIENCE 各 1 个没有卡）、25 条关联；再确认一次返回 409。随后导入 5 道新题抽取：和已确认知识点重复的 2 题写进了 covered（引用的是知识点 id），另外 3 题生成新知识点。这也补上了决策 014 中“已有知识点这一来源还没在真实流程中验证”的遗留问题

## 理由

- **传取消的 id**：和“逐条取消勾选”的操作一致，默认全部接受，请求也短
- **只有 READY 能确认**：部分失败时确认，失败批次中的题会无声地丢掉；先重试成本很低
- **全部取消也能确认**：草稿需要一个“处理完了”的终点，否则全都不要的草稿会一直挂着
- **knowledge 决定是否调度**：review 只通过 kp_id 工作（决策 002），类型属于知识点的内容
- **创建知识点的逻辑放在 KnowledgePointService**：以后由学习会话生成知识点（#31）也走这里，sort_order、关联材料、初始化调度状态不用再写一遍

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 请求中传勾选的 id | 多数情况下要把几十个 id 全部传一遍 |
| 部分失败的草稿也能确认 | 失败批次中的题会无声地丢掉 |
| 全部取消时报错 | 全都不要的草稿没有办法结束 |
| 草稿上存 CONFIRMED 状态 | 和由批次推算的状态混在一起，要保证两者一致 |
| 条目上记 kp_id，知识点上不记来源 | issue 要求知识点记录来源；从知识点出发对比 AI 输出更常用 |
| review 根据类型自己判断要不要初始化 | review 就得知道知识点的类型，违反决策 002 |
| 引入 ArchUnit 检查依赖 | 需要新依赖；目前只有一条规则，扫描源码就够了 |

## 遗留问题

- sort_order 取“当前最大值 + 1”：同一个用户的两份草稿同时确认时，可能得到相同的 sort_order。派发时相同的按 id 排序，不会出错，只是两批知识点会交错。单用户手动确认，几乎不会同时发生，不加锁
- covered 被误判时，用户不能选择“仍然新建”：被误判的题没有对应的条目，要新建就得重新抽取。以后可以在 #25（编辑知识点）中手动补
- 确认后不能撤销。要撤销得删除知识点和调度状态，留给 #25
