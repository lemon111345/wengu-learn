# 039 修改评分

## 背景

自用中发现（#84）：评分页选了一档之后就不能再改，误触很常见。比如 HashMap 复习时 AI 建议“困难”，却评成了“简单”，下次复习被排到 13 天后。影响不止下一次的日期：评分会改变 FSRS 的稳定性 S 和难度 D，之后每次复习都在这个基础上计算，误差会一路带下去。

要定的是：改分怎么算才准确、数据存在哪、接口怎么变、哪些评分能改。

## 决策

### 1. 评分时存快照，改分时恢复快照重算

- `review_log` 新增 `step_before`、`stability_before`、`difficulty_before`、`due_before`、`last_review_before`（V13，可空，类型和 `card_state` 相同），和已有的 `state_before` 合起来是一张完整的卡片
- 修改评分：恢复快照，用**原来的评分时间**（`reviewed_at`）按新评分重算，更新 `card_state` 和这条流水的 `rating_user`、`due_after`，在一个事务里完成
- `reviewed_at`、`is_first_review`、`rating_ai` 和快照都不变，所以新学名额的计算不受影响，反复改也不会累积误差
- fuzz 的随机数由“知识点 + 上次复习时间”决定（决策 026），恢复快照后上次复习时间相同，结果确定：**改分的结果和第一次就选这一档完全相同**
- `review.fsrs` 不用改，仍然只放纯计算代码

**两个实现细节：**

- **用 `due_before` 判断有没有快照**：`card_state.due` 不为空，而新卡的 S、D、`last_review` 本来就是空的，不能用它们判断
- **计算前把评分时间截断到毫秒**：数据库只存到毫秒，不截断的话，改分时读回的时间和第一次计算用的不同，结果不一定完全一样

### 2. 只能改这个知识点最近一次的评分，不设期限

- 之后又复习过的不能改：后面的评分是在这次的结果上算的，改了这次，后面的就对不上了
- V13 之前的记录没有快照，不能改
- 不设时间期限：规则简单，也不用再定一个期限。隔几天再改时仍然按原来的评分时间计算，到期时间可能已经过去，这时 `days` 为负，前端显示“今天”

### 3. 接口沿用 `POST /api/sessions/{id}/rating`

- 含义从“确认评分”变成“设定这次学习的评分”：没评过就是评分，评过就是修改
- `GET /api/sessions/{id}/rating-preview` 对能修改的已评分会话也返回结果，按快照计算；不能修改的返回 409
- `SessionView` 新增 `ratingEditable`，能不能改由后端判断，客户端只负责显示（决策 034）
- 已评过分时第二次提交从 409 变成 200，字段都没变。旧客户端不会主动重复提交，不受影响

### 4. “今天已完成”和 AI 建议

- `study_day_completion` 不撤销：决策 020 把它定义为已经发生的事实。项目没有学习步（决策 003），评分当天改成“忘了”也至少隔一天到期，当天的计划不会多出来；隔几天再改时，到期的卡出现在改分当天的计划中，和之前哪天完成没有关系
- `rating_ai` 不变，保留的是第一次评分时的 AI 建议

### 5. 前端

- 按钮选中后不禁用，点另一档或按 1～4 就是修改，日期立刻变，后台保存（ui.md 5.4）
- 同一时间只发一个请求，连续快速改分时等前一个返回后只发最后一次的选择，过时的响应不显示
- 保存失败退回上一次保存成功的评分

## 理由

- **不能在已经按旧评分算过的状态上再算**：FSRS 是非线性的，难度还会被截在 1～10，无法倒推出评分前的状态，必须事先存下来
- **快照放在 `review_log`**：一次评分对应一份快照，生命周期相同，也正好用来判断“能不能改”；新建一张表要多一次关联，没有好处
- **沿用 `POST`**：前端不用区分第一次评分和修改；第一次请求其实已保存、前端却以为失败时，重试也不会报 409

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 从第一次评分开始按 FSRS 重放全部历史 | 不用迁移、旧记录也能改，但依赖“重放结果与当初完全一致”，也会掩盖其他问题 |
| 新增 `PUT /api/sessions/{id}/rating` | 语义更清楚，但客户端要先判断该调哪个接口，两个接口的返回和规则也基本重复 |
| 给旧记录补快照 | 只有第一次评分能可靠推出评分前的状态，补上后规则会变成“部分旧记录能改” |
| 只允许当天修改 | 多一条规则，还要定“当天”的边界；误触隔天才发现也应该能改 |
| 改分时撤销“当天完成” | 它记录的是已经发生的事实（决策 020），而且当天改分不会让计划多出来 |
