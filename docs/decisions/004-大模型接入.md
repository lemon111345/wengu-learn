# 004 大模型接入

## 背景

知识点抽取（#3）和学习对话都依赖大模型。M0 需要先验证后端能通过配置连接一个兼容 OpenAI 格式的模型，跑通普通调用和流式调用（issue #2）。约束：API Key 只能从环境变量读取，不得出现在代码、配置文件、日志和提交历史中；没有配置 Key 时应用也要能启动。

## 决策

### 1. 使用 Spring AI 2.0.1 的 OpenAI starter

- 版本：Spring AI 2.0.1（2026-08-21 发布，接入时的最新稳定版；2.1.0 仍为里程碑版）
- 2.0.1 的 starter 依赖 `spring-boot-starter-webclient:4.1.1` / `restclient:4.1.1`，与项目的 Spring Boot 4.1.1 一致
- 用 `spring-ai-bom` 统一管理 Spring AI 各模块的版本
- 选 `spring-ai-starter-model-openai` 而不是 DeepSeek 专用 starter：换成任何兼容 OpenAI 格式的服务（通义千问、Kimi、Ollama 等）只需改环境变量

### 2. 配置只来自项目自己的环境变量

| 环境变量 | 映射到 | 默认值 |
| --- | --- | --- |
| `WENGU_LLM_BASE_URL` | `spring.ai.openai.base-url` | `https://api.deepseek.com` |
| `WENGU_LLM_API_KEY` | `spring.ai.openai.api-key` | 空字符串 |
| `WENGU_LLM_MODEL` | `spring.ai.openai.chat.options.model` | `deepseek-flash` |

默认使用 DeepSeek：作者使用的服务，价格低、速度快，适合验证。

### 3. 处理 Spring AI 的两个隐含行为

阅读源码（`OpenAiSetup`）发现：

- 配置中没有 `api-key` 时，会读取 `OPENAI_API_KEY` 环境变量；没有 `base-url` 时，会读取 `OPENAI_BASE_URL`。本机若因其他工具设置过这两个变量，会在不知情的情况下用错 Key 或连错服务
- `api-key` 为空字符串时进入“无认证模式”，请求不带 Authorization 头

做法：两项都在 yml 中**显式给出值**（api-key 默认空字符串），隐式读取不会发生；空 Key 时应用照常启动，调用时由服务端返回 401；连本地 Ollama 时不设 Key 即可。

### 4. base-url 原样使用，不会自动补 /v1

Spring AI 2.0 改用 OpenAI 官方 Java SDK，base-url 原样传给 SDK，SDK 只拼接 `/chat/completions`（1.x 会自动拼 `/v1`）。因此 DeepSeek 写 `https://api.deepseek.com`，OpenAI 必须写 `https://api.openai.com/v1`，Ollama 写 `http://localhost:11434/v1`。写在 yml 注释和 README 中。

### 5. llm 模块用 LlmService 隔离 Spring AI

- `LlmService.call(prompt)` 返回完整回复，`stream(prompt)` 返回 `Flux<String>`
- 其他模块只通过 LlmService 调用大模型，不直接使用 Spring AI（决策 002 的模块边界）
- 以后的降级链、按用户读取 model_config 都在 LlmService 内部实现，调用方不用改
- 目前只提供最简单的“prompt → 回复”，system prompt、结构化输出等按需在 #3 中增加

### 6. 实连测试显式开启

- `LlmServiceLiveTest` 用 `@EnabledIfSystemProperty(named = "llm.live", matches = "true")`，普通 `mvnw test` 跳过
- 流式测试断言收到**多于一段**内容，否则说明并非真正的流式返回
- 实测（DeepSeek `deepseek-flash`）：普通调用返回完整句子，流式调用分 39 段返回；测试输出和 `target/` 下所有文件中 Key 出现 0 次

### 7. M0 使用全局配置

M0 只有一套来自环境变量的全局配置。技术方案中按用户存储的 model_config（加密的 Key）属于 M3 多用户模式；届时 LlmService 改为按用户配置以编程方式创建模型客户端，自动配置可能随之关闭。

## 理由

- **Spring AI**：技术方案已选定；与 Spring Boot 的配置、依赖注入方式一致，流式输出直接得到 `Flux`，以后 SSE 接口可直接返回
- **项目自己的环境变量名**：`WENGU_LLM_*` 一眼可知归属；Spring AI 以后改属性名只需改 yml，Docker Compose 等部署配置不变
- **显式给值**：关掉隐含行为，配置来源只有一处，排查问题时不用猜
- **系统属性开关**：全局设置了 Key 的机器上，每次 `mvnw test` 都真实调用模型既花钱又慢，显式开启才不会误触发

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| DeepSeek 专用 starter | 绑定单一服务商，换服务要换依赖 |
| 直接使用 OpenAI 官方 Java SDK | 要自己处理流式、配置绑定、重试；Spring AI 已经封装好，且与 Spring 生态一致 |
| 直接用 Spring 的属性名环境变量（`SPRING_AI_OPENAI_API_KEY`） | 名字随 Spring AI 变化；不能一眼看出是本项目的配置 |
| 不设 api-key 默认值 | 会隐式读取 `OPENAI_API_KEY` |
| 关闭自动配置（`spring.ai.model.chat=none`）以支持无 Key 启动 | 实测空 Key 时应用可以正常启动，不需要 |
| 检测到 Key 就运行实连测试 | 全局设置 Key 后每次测试都产生费用 |
| 其他模块直接注入 `ChatClient` | 降级链和按用户配置无处可加，每个调用方都要改 |

## 依赖说明

starter 会间接引入：OpenAI 官方 Java SDK（`openai-java-core` 4.49.0）、OkHttp、Kotlin 标准库（SDK 用 Kotlin 编写）、Reactor 与 Netty（WebClient 与流式输出）、Jackson 2（SDK 使用，与 Spring Boot 4 的 Jackson 3 包名不同，可共存）。`azure-identity` 为可选依赖，不会引入。应用仍运行在 Tomcat 上。
