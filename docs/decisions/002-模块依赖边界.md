# 002 模块依赖边界

## 背景

项目是按业务分包的模块化单体。最初的约定只规定了“plan 依赖 review 和 knowledge，反之不行”，其他模块之间的关系没有明确：llm 读模型配置是否依赖 user、review 是否需要知道知识点内容、各模块如何拿到当前用户，都没有定论。依赖关系一旦在代码里长出环，后面很难再拆开，所以在写业务代码之前先定下来。

## 决策

完整依赖关系（所有模块都可以依赖 common，不再列出）：

| 模块 | 可以依赖的业务模块 |
| --- | --- |
| plan | knowledge、review、user |
| chat | knowledge、llm、review |
| knowledge | source、llm、review |
| source | llm |
| review、llm、user | 无 |

补充规则：

1. **review 只通过 kp_id 工作，绝不能依赖 knowledge。** 知识点创建时，由 knowledge 调用 review 初始化调度状态。
2. **model_config 归 llm 管理**，llm 是不依赖任何业务模块的底层模块。
3. **获取当前用户 id 的能力放在 common**，单用户模式下返回默认用户。各模块不为获取用户 id 而依赖 user。
4. **plan 只通过 user 的 Service 读取用户设置**（时区、day_start_hour、每天新学数量），不访问 user_settings 表。
5. **结束评分由 chat 调用 review。** 用户确认评分后，chat 核对会话，再调用 ReviewService 更新 card_state、写 review_log（含 session_id 和 AI 建议的评分 rating_ai）。
6. **每日计划的跨模块查询分两步：**
   - 哪些知识点有调度状态，由 knowledge 在创建时决定：SYSTEM_DESIGN 类型不初始化 card_state（M1 中 EXPERIENCE 也不初始化，见[决策 007](./007-M1范围与设计调整.md)），所以它们不会进入每日计划
   - plan 先从 review 取出候选 kp_id（到期复习、新知识两组），再交给 knowledge 在内存中按状态过滤（排除暂停的）、按 knowledge_point 的排序字段排序。排序用明确的字段，不依赖创建时间：同一批插入的时间戳相同，以后合并、插入知识点时顺序也会乱
   - **这是有意的取舍**：MVP 只有几百个知识点，在内存中过滤和排序足够快。知识点到几千个以后，大的 IN 列表和内存排序可能成为瓶颈，到时再改

## 理由

- **严格分层、没有环**：review、llm、user 在最底层，source 只依赖 llm，knowledge 在中间，plan、chat 在上层。每层只依赖下层，可以从下往上逐层开发和测试，底层模块能独立做单元测试。
- **review 保持通用**：调度只关心“某个 id 的卡片现在什么状态、得了几分”。不依赖 knowledge，以后要调度别的东西（如源码片段）也不用改 review；由更具体的 knowledge 调用更通用的 review，方向正确。
- **llm 复用面最广**：knowledge 和 chat 都要用大模型。llm 若依赖 user，上层会被间接拖进 user；model_config 只有 llm 使用，放在 llm 也符合“模块只访问自己的表”。
- **用户 id 放 common 支撑运行模式切换**：业务代码只调用一个方法拿 user_id，单用户 / 多用户的差异集中在 common 一处，不会写出两套代码；user 也不会变成被所有模块依赖的中心节点。
- **plan → user**：计算每日计划必须读用户设置。user 是叶子模块，加这一条不会产生环，是改动最小的做法。
- **chat → review**：评分发生在学习会话结束时，只有 chat 知道 session 是否属于当前用户、是否已经评过分，rating_ai 也由 chat 从对话中得到，不经过客户端。review 仍然不依赖任何业务模块，加这一条不会产生环。
- **source → llm**：source 要调用模型把用户粘贴的资料切分成题目，切分结果存在 source 表，写入方必须是 source。llm 是最底层的模块，加这一条不会产生环，见[决策 011](./011-题目切分交给模型.md)。
- **每日计划分两步查询**：每个模块只读自己的表，review 不需要了解知识点的状态和顺序，knowledge 不需要了解调度。

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| llm 依赖 user 读取模型配置 | llm 变成非底层模块，knowledge、chat 被间接拖入对 user 的依赖 |
| review 依赖 knowledge（例如自己查知识点信息） | review 与知识点内容耦合，无法复用；容易和 knowledge → review 形成环 |
| 各模块依赖 user 获取当前用户 id | user 成为几乎所有模块都依赖的中心节点，运行模式切换的逻辑也会分散 |
| common 提供包含时区等设置的“用户上下文”，plan 不依赖 user | common 要了解用户设置的结构，基础层变重，职责不清 |
| 结束评分时前端直接调用 review 的接口 | rating_ai 要由客户端传入，可以被篡改；review 也无法核对 session |
| plan 关联查询 card_state 和 knowledge_point | plan 直接访问两个模块的表，违反“模块只访问自己的表” |
| 所有知识点都初始化 card_state，由 plan 按类型排除 | plan 要了解哪些类型不参与调度；card_state 中会有永远不会派发的卡 |
