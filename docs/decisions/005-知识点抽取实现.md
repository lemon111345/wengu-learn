# 005 知识点抽取实现

## 背景

M0 要验证“AI 抽取知识点”的质量（issue #3）：用约 30 道样本题调用模型，输出结构化的知识点，交给作者人工标注。本记录只写实现层面的选择：调用方式、输出结构、校验和实验方法。粒度标准和 prompt 内容的结论见 #4 的决策记录。

实验设置：样本 30 道 Java 后端面试题（来自私人题库，只放在 `data-private/`，不进仓库）；模型 DeepSeek `deepseek-flash`；共跑了 v1～v3 三版 prompt。

## 决策

### 1. 所有题目一次请求发给模型

`KnowledgeExtractionService.extract()` 把整批题目拼成一条用户消息，每行 `[题号] 题目`，只调用一次模型。模型同时看到所有题，才能把“问法不同、考的是同一内容”的题合并，或者把大题拆出的追问并入另一道题。逐题调用时，合并在结构上就不可能发生。

### 2. 结构化输出 + 独立校验

- `LlmService.call(system, user, type)` 用 Spring AI 的 `BeanOutputConverter`：根据 record 生成 JSON Schema 追加在用户消息末尾，再把回复解析成对象。解析失败抛 `LlmOutputParseException`，携带原始输出
- JSON 能解析不代表结果可用：模型可能漏题、编造题号、order 不连续、标题重复。`ExtractionValidator` 是纯函数，单独检查这些硬性要求，有单元测试

### 3. temperature 由调用方指定，抽取用 0.2

- `LlmService` 新增重载 `call(system, user, type, temperature)`，只对这一次请求生效；传 null 时使用服务商默认值
- 实测：v2 prompt 在默认 temperature（DeepSeek 为 1.0）下两次分别输出 29 和 41 个知识点，拆分和合并的位置也完全不同；改为 0.2 后两次为 33 和 34，结构基本一致
- temperature 和 prompt 版本一起决定抽取效果，所以 `TEMPERATURE` 常量与 `PROMPT_VERSION` 放在一起，并记入每次实验的 meta.json

### 4. 先输出主题分组，再输出知识点

- `ExtractionResult` 增加 `groups` 字段（`TopicGroup`：主题、题号、重叠判断），排在 `knowledgePoints` 前面。模型按顺序生成，写知识点时，刚写下的分组和“哪些题考的是同一内容”的判断就在上下文里
- groups 只是推理草稿，不入库
- 效果（v3 对比 v2，temperature 都是 0.2）：分组 3 轮完全一致；v2 中只偶尔合并的几组题，v3 中 3 轮都合并了。附带的好处是能读到模型不合并的理由，便于判断它是判断错了还是没比较
- **注意**：Spring AI 生成的 JSON Schema 按字段名字母排序，不按 record 声明顺序。groups 排在前面是因为 g 在 k 前面，改字段名时要保持这个顺序

### 5. prompt 按版本存成文件

- prompt 放在 `resources/prompts/knowledge-extraction-vN.md`，调整时新增文件、旧版本保留，便于对比
- 示例题目刻意避开样本题：如果示例就是样本里的题，模型照抄示例就能“做对”，实验测不出真实效果

### 6. 实验入口显式开启，结果只写到 data-private

- `KnowledgeExtractionExperiment` 用 `@EnabledIfSystemProperty(named = "llm.experiment", matches = "true")`，普通测试跳过
- 每次运行写入 `data-private/experiments/时间戳-模型名/`：原始输出、解析结果、meta.json（模型、prompt 版本、temperature、耗时、token、校验问题），以及供人工标注的 CSV（带 BOM，Excel 直接打开不乱码）
- 解析失败时也保存原始输出

### 7. 请求超时可配置

Spring AI 默认 60 秒超时，长输出会超时。改为 `WENGU_LLM_TIMEOUT`，默认 180 秒。

## 理由

- **一次请求**：合并是抽取规则的核心，只有一次请求能做到；30 道题连同 system prompt 的输入约 3000 token，远小于上下文上限
- **独立校验器**：模型输出的问题大多不会导致解析失败，必须单独检查；纯函数便于测试
- **调用方指定 temperature**：不同任务要求不同，抽取要稳定，学习对话需要一些自然度，以后“换角度提问”甚至需要多样性
- **分组字段**：只在 prompt 里要求“先归组再合并”，模型可以跳过这一步；变成必须输出的字段后，它就跳不过了

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 逐题调用 | 无法跨题合并 |
| 两步调用：先拆分，再单独请求去重合并 | 更可控，但调用次数和代码都翻倍，M0 不值得 |
| 在 application.yml 设全局 temperature | 会让以后的学习对话也变得死板 |
| 结构化调用一律在内部使用低 temperature | 不是所有结构化任务都要稳定，规则藏在 llm 模块里不合适 |
| 用 options 对象封装 temperature、maxTokens 等 | 现在只需要一个参数，属于过度设计 |
| 通用的 `thinking` 字符串字段代替 groups | 模型可能写得很随意；按主题分组的结构能迫使它把每道题都过一遍 |
| overlaps 做成结构化列表，由程序检查合并是否兑现 | schema 更复杂；目前只需要让模型把推理写出来 |
| 通过配置切换 prompt 版本 | 只有实验会切换，改常量就够了 |

## 遗留问题

- `deepseek-v4-pro` 两次超时（60 秒、180 秒），原因未查，M0 先用 flash
- 有一次返回的正文为空（结束原因 STOP，却计费了 3727 个输出 token），解析失败。计费 token 普遍多于实际输出的字数，疑似模型有隐藏推理，空正文可能是内容落在了推理字段里，未查实。产品中如果偶发，需要加重试
