# 025 学习会话与流式对话

## 背景

#19 实现学习一个知识点的后端：开始学习、老师流式回复、消息存库、自动计时。要定的是：

- SSE 用什么请求方式（浏览器的 EventSource 只能发 GET）
- 用户消息、AI 消息分别在什么时候存；浏览器中途断开、模型出错时怎么办
- 会话什么时候算结束
- 自动计时怎么排除不活动的时间（决策 008 第 6 条）
- 学习对话 prompt 要输出【完整作答】标记，还要支持“这个我会，直接完整作答”（决策 018）
- 今天页的“今天已学 X 分钟”从哪里来（决策 024 留给本 issue）

“接着问”用单独的 prompt，和本记录的流程相对独立，在 #19 的第二个 PR 中实现。

## 决策

### 1. SSE 用 POST，前端用 fetch 读流

`POST /api/sessions/{id}/messages` 的响应直接是 `text/event-stream`：一个请求既带上学生的回答，又收回老师的回复。CSRF 令牌照常放在请求头里，回答内容不出现在 URL 和访问日志里。

推送三种事件：`delta`（一段文字）、`done`（存库后的消息 id、标记、会话是否结束）、`error`（可以直接显示的提示）。

校验在开始推送之前同步完成，不通过时返回统一格式的 JSON 错误（如轮到老师回复时发消息为 409），前端按普通接口处理。

### 2. 消息的存库时机

- 学生的消息一收到就存，并记一次活动
- 老师的回复生成完时存完整的文本
- **模型生成和浏览器连接分开**：保存回复的订阅先于推给前端的订阅建立，模型的输出用 `cache()` 让两者共用一次调用。浏览器断开只取消推送，模型照常生成完、存进库，刷新后能看到完整的回复
- 模型出错或返回空回复时不存，推送 `error`；学生的消息已经存下，`POST /api/sessions/{id}/reply` 重新生成这一条回复
- 同一个会话同时只生成一条回复，正在生成的会话记在内存中（单实例部署），后到的请求返回 409。后端重启后这个记录清空，没存下的回复由用户重试
- 存库是阻塞的 JDBC 调用，放到 `boundedElastic` 线程上做，不占用模型客户端的网络线程
- Spring MVC 异步请求的超时改为 10 分钟，要比模型的单次请求超时长；超时只断开连接，回复照常在后台生成、存库

### 3. 标记从流中去掉，记在消息上

模型在要求完整作答时输出【完整作答】，收尾时输出【学习结束】。后端识别后从推送的文字和存库的内容中去掉，记在 `message.marker` 上（`RESTATE` / `END`），并在 `done` 事件中告诉前端。

流式输出时一个标记可能被拆在两段里（如“【学习”和“结束】”）。每段结尾处可能是标记开头的那几个字先压住，等下一段来了再判断，不是标记就原样放出（`MarkerFilter`）。

### 4. 会话的开始与结束

- `POST /api/sessions` 只创建会话，不调用模型；老师的第一句由前端接着调用 `reply` 生成。这个知识点有没结束的会话时，返回那个会话，接着学，刷新、离开后再回来都走这里
- 模型输出【学习结束】，或者学生已回答 8 次（决策 008 第 3 条）时，会话结束（`ended_at`），之后进入评分（#20）
- 不做“放弃”和超时
- 只收录的类型（系统设计、个人经历）不能开始学习

### 5. 发给模型的消息

- system prompt 不变；第一条用户消息是知识点信息（标题、类型、要点、来源面试题），**不存库**，每次由 knowledge 的学习材料现拼
- 附在学生消息后面、只给模型看的提示（第 7 次回答的“只剩最后一轮”、第 8 次的“已达到最大轮数”、跳过讲解的提示）存在 `message.model_note`，重建历史时原样带上；前端不显示
- 老师的回复重建历史时把标记补回去，和模型当时的输出一致
- 来源面试题经“知识点 → 草稿条目 → 材料中的题”找到，带上追问

### 6. 学习对话 prompt v3

在 v2 上加两条：要求完整作答时，回复最后另起一行输出【完整作答】；学生消息注明“学生选择跳过讲解”时，直接进入完整作答。没有重跑 #14 的实验，自用阶段观察。实连测试（`ChatLiveTest`）确认模型照做了这两个标记。

“这个我会，直接完整作答”在对话中显示为一条学生消息“这个我会，直接完整作答。”，附上跳过讲解的提示，会话上记录 `skipped_explanation`。已经在完整作答时不能再跳过。

### 7. 有效时长：两次活动之间最多算 10 分钟

活动指会话开始、学生发消息、老师回复完。每次活动把距上次活动的时间加进 `active_seconds`，超过 10 分钟的只算 10 分钟。

今天页的“今天已学 X 分钟”是今天学习日内开始的会话的有效时长之和（不足一分钟舍去）。跨过分界时刻的会话整个算在开始的那天。为此 **plan 新增对 chat 的依赖**（决策 002 已修订）。

## 理由

- **POST + fetch**：EventSource 只能发 GET，要么把回答放进 URL，要么先 POST 再开一个 GET 接回复，服务端还得在两个请求之间维持“这条回复属于哪次提问”的状态
- **断开后照样存**：学生的回答已经存下，老师的回复也应该完整；token 照样花掉，但很少。断开就丢掉回复的话，刷新后只能重新生成，花得更多
- **第一条消息不存**：它是知识点的派生数据，存下来要处理知识点修改后的不一致；现拼的代价只是一次查询
- **提示存库**：轮数提示由“第几次回答”决定，跳过讲解的提示由用户的操作决定，事后推算不出来；不存的话，重建的历史和模型当时看到的不一样
- **间隔封顶而不是超时清零**：认真写了 12 分钟的完整作答不该整段扣掉；中途离开半小时，也只多算 10 分钟
- **plan → chat**：分钟数是会话上的事实，chat 不依赖 plan，加这一条不会产生环

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| EventSource（GET） | 带不上回答内容和 CSRF 令牌；拆成两个请求要在服务端维持状态 |
| 浏览器断开时取消模型调用 | 刷新后看不到这条回复，要重新生成 |
| 断开时保存已生成的一半 | 半句话的回复没有用，学生也没法接着回答 |
| 第一条消息（知识点信息）存库 | 知识点修改后不一致；派生数据不存 |
| 用一个状态字段表示“正在完整作答”“已结束” | 从最后一条老师回复的标记和 `ended_at` 就能推出，不另存 |
| 超过阈值没有输入就整段不计时 | 写得慢的完整作答会被整段扣掉 |
| 分钟数留到 M2 的统计页 | 今天页的设计里就有，数据已经在会话上 |
| “这个我会”只记在会话上，不出现在对话中 | 前端恢复历史时看不出为什么老师突然要求完整作答 |

## 遗留问题

- “正在生成”只记在内存中，多实例部署时要换成数据库或 Redis 中的锁
- 一条回复生成到一半时后端重启，这条回复丢失，学生的消息还在，由用户重试
- 会话结束后，刚存完回复、还没清掉“正在生成”的一瞬间再发请求会得到 409，前端稍后重试即可
- 没结束的会话一直保留，隔了很多天再打开也接着上次的对话；需要时再加“过期后重新开始”
- 友好的出错提示（模型 401、超时）由 #27 细化，现在统一显示“老师暂时没有回应，可以点重试”
