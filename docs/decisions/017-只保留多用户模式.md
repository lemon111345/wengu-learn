# 017 只保留多用户模式，不设管理员

## 背景

原计划是自部署和线上版用同一套代码，通过配置切换“单用户模式 / 多用户模式”：M1 只做单用户，当前用户固定为 V1 插入的默认用户（决策 002 第 3 条、决策 009 第 5 条）；账号、注册登录放在 M3。

设计前端时发现，两种模式虽然共用一套代码，但界面要分两套：单用户没有登录页和账户区，配置切换还会让“部署、模式、管理员”之类的文字出现在界面上。线上版本来就要注册登录，M3 时 `CurrentUser`、所有接口的鉴权、前端的登录态都要再改一遍。

## 决策

1. **只保留多用户模式**：自部署和线上版都要注册登录。Spring Security 始终启用，去掉单用户 / 多用户的配置切换
2. **不设管理员**：不区分角色，所有用户平等
3. **是否开放注册由环境变量 `WENGU_ALLOW_REGISTRATION` 控制**。自部署的人按 README 先注册自己，再关掉注册
4. **界面上不出现部署、配置、管理员相关的文字**，这些写在 README
5. **注册时从浏览器读取时区，静默提交**；读不到或不合法时用 `WENGU_TIMEZONE`
6. **M1 的模型配置仍是整个部署共用一套**，由环境变量提供（决策 007 不变）。每个用户自带 Key、加密存储、免费额度、限流仍在 M3
7. **登录凭证的存放方式在“账号与登录” issue 的方案中比较**，另写决策记录。要考虑的是：浏览器的 EventSource 不能设置请求头，学习对话的 SSE 带不上 Authorization 头。候选是 HttpOnly Cookie（服务端 Session，或 Cookie 中的 JWT，含 CSRF 处理）和请求头中的 JWT（流式接口改用 fetch 读取），倾向前者
8. **V1 插入的默认用户**（id 1，用户名 `default`，没有密码）：迁移脚本只删除没有业务数据的默认用户。“业务数据”指资料、知识点、会话等，不包括 user_settings；删除默认用户时，它的 user_settings 一并删除。作者本地开发库中已有的数据，用一段一次性 SQL 转给作者新注册的账号（各表的 user_id 从 1 改为新用户 id），脚本放在 `tools/`，不进迁移

## 理由

- **一种模式就是一条路径**：配置切换的代价不在代码行数，而在界面、测试和文档都要覆盖两种情况。只做多用户，M1 实现的就是最终形态，M3 不用回头改鉴权
- **自部署多注册一次，成本很低**：注册一次、改一个环境变量，换来界面上没有任何部署相关的概念
- **不设管理员**：M1 没有任何管理员专属的功能，模型配置和注册开关都来自环境变量。设了管理员，就要多一个角色字段和一套权限判断，却没有地方用
- **注册开关放环境变量**：开关属于部署，不属于产品界面；和模型配置的做法一致
- **时区静默提交**：用户不需要知道时区这个概念，读浏览器的设置就够准；设置页可以再改
- **默认用户只删空的**：新部署中默认用户是一个登不上的空账号，还占着用户名 `default`，应当删掉；有数据的库不能由迁移脚本替用户决定数据归谁。作者本地的数据只此一份，用一次性脚本处理，不让所有部署都执行它

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 保留单用户 / 多用户两种模式，用配置切换 | 界面、测试、文档都要覆盖两种情况；M3 还要回头改鉴权 |
| 第一个注册的用户为管理员 | 管理员在 M1 没有任何专属功能；部署后谁先注册谁就是管理员，还要多一套角色判断 |
| 注册开关放在设置页，由管理员控制 | 需要管理员；开关属于部署配置 |
| 注册时让用户选时区 | 多一个用户不理解的问题，浏览器已经知道答案 |
| 迁移脚本把默认用户的数据转给第一个注册的用户 | 等于让第一个注册的人接管已有数据，规则隐蔽；只有作者本地有这种数据 |
| 迁移脚本保留默认用户不动 | 留下一个登不上的账号，还占着用户名 |

## 遗留问题

- 所有用户共用部署者的模型配置，调用都花部署者的 Key。开放注册的部署在 M3 有限流之前，只能靠关掉注册来控制
- 绑定邮箱、找回密码、防批量注册在 PRD 的“上线前必须完成”清单中，M1 不做。M1 忘记密码只能由部署者改库
