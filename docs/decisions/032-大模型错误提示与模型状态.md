# 032 大模型错误提示与模型状态

## 背景

#27 之前，模型出错时用户看到的提示很笼统，有时还是 500：

| 场景 | 原来的处理 | 用户看到的 |
| --- | --- | --- |
| 题目切分（同步） | 只捕获输出解析失败；Key 不对、超时一路抛到兜底 | 500“服务器内部错误” |
| 后台抽取 | 批次标为 FAILED，`error` 记异常类名，不返回前端（决策 013） | “这一批没抽出来”，没有原因 |
| 学习对话（流式） | 所有错误、包括空回复，都是同一句 | “老师暂时没有回应，可以点重试” |
| 评分建议 | 统一返回 `RATING_SUGGESTION_FAILED` | 只说没生成出来 |

issue 要求区分 Key 错误、超时、空正文三类，空正文是否重试在方案中定；设计交接（#44）补充了模型状态接口：模型名、最近一次调用的结果和时间，设置页和头像红点用它。另外要用本地 Ollama 实测一次。

## 决策

### 1. 在 llm 模块统一分类

`LlmService` 的所有调用（同步、流式）都把 SDK 的异常转成 `LlmException`。它继承 common 的 `BusinessException`，带上返回码：

- 调用方不用认识 openai-java 的各种异常类
- 没有被调用方处理的，由现有的全局异常处理器直接返回对应的状态码和提示，不用新写处理器
- 输出解析失败不算调用失败，仍然是 `LlmOutputParseException`：模型回应了，只是内容不合格，调用方可以重试

分类规则沿异常链判断，先看具体的再看笼统的（超时和连不上都是 `OpenAIIoException`，要先找超时）。SDK 实际抛出的异常用假的模型服务实测过（`LlmErrorTest`）：

| SDK 抛出 | 返回码 | 状态码 | 提示 |
| --- | --- | --- | --- |
| `UnauthorizedException`、`PermissionDeniedException`（401、403） | `LLM_AUTH_FAILED` | 502 | AI 模型拒绝了请求，可能是 API Key 不对或已经失效 |
| `NotFoundException`（404） | `LLM_MODEL_NOT_FOUND` | 502 | 找不到配置的 AI 模型，可能是模型名不对 |
| `RateLimitException`（429） | `LLM_RATE_LIMITED` | 502 | AI 模型的调用太频繁或额度用完了，请稍后再试 |
| 原因链中有 `InterruptedIOException` | `LLM_TIMEOUT` | 504 | AI 模型太久没有回应，可以重试 |
| 正常结束但没有正文 | `LLM_EMPTY_RESPONSE` | 502 | AI 模型没有返回内容，可以重试；反复出现时，可能是模型只输出了思考过程 |
| `OpenAIIoException`、5xx、其他 IOException | `LLM_UNAVAILABLE` | 502 | 连不上 AI 模型，可以重试 |
| 其他（如 400） | `LLM_FAILED` | 502 | AI 模型调用失败，可以重试 |

- 流式调用的异常外面多包一层 `CompletionException`，沿异常链判断不受影响
- issue 只要求前三类；404、429、连不上是顺手分出来的：本地 Ollama 没启动、模型没下载时最常见
- 提示只讲现象和怎么办，不提环境变量（ui.md 设计原则 5）

### 2. 空正文：不自动重试

- **实测**：流式调用正常结束却一个字都没有时，SDK 不报错；同步调用会被当成“JSON 解析失败”，调用方会重试
- `LlmService` 主动判断：同步调用在解析前看原文是否为空（被截断的除外，那是输出问题），流式调用结束时看有没有收到任何文字
- 学习对话中去掉标记后没有正文（只输出了【学习结束】），也按空正文提示
- **不重试**：空正文多半是模型本身的问题（推理模型把回答放进思考内容），重试一次通常还是空的，只让用户多等一轮

### 3. 各场景接上分类

| 场景 | 做法 |
| --- | --- |
| 题目切分 | `LlmException` 直接抛出，返回对应的返回码；输出解析失败仍是 `QUESTION_SPLIT_FAILED` |
| 后台抽取 | V12 给 `extraction_batch` 加 `error_code`：调用失败记分类的返回码，不是 `LlmException` 的记 `LLM_FAILED`，输出重试后仍不合格记 `LLM_INVALID_OUTPUT`；因此没执行的批次沿用前一批的返回码。草稿的批次返回 `failureReason`（由返回码得出提示），原始的 `error` 仍不返回 |
| 学习对话 | `error` 事件的提示按分类给出，原因不明时仍是“老师暂时没有回应，可以点重试” |
| 评分建议 | 返回码仍是 `RATING_SUGGESTION_FAILED`（前端据此知道可以直接评分），提示改为“AI 评分建议没有生成出来：<原因>。也可以直接评分” |

### 4. 模型状态：内存中的最近一次结果

- `LlmStatusTracker` 记下最近一次调用的结果：成功，或失败的返回码、提示、时间。输出不合格算成功：模型有回应，是内容的问题
- `GET /api/llm/status` 返回 `{model, lastCall}`，不返回服务地址和 Key，不为此真实调用模型
- **存在内存中**，重启后为 null；**全局的**：M1 所有用户共用一套模型配置（环境变量）
- 这是 llm 模块的第一个 Controller

### 5. 前端

- 抽取进度：失败的批次在进度条下面显示原因
- 头像上的红点：进入应用和每次切换页面时取一次模型状态，最近一次失败时显示红点（`--wg-warn`）；账户菜单中第一行写明原因。设置页（#52）做好后，原因改由它的 AI 模型卡片显示（ui.md 第 7 节）
- 导入、学习对话、评分建议原本就显示后端的 `message`，不用改

## 理由

- **分类放在 llm**：只有它认识 SDK；调用方按返回码处理，换 SDK 或加降级链时只改一处
- **继承 BusinessException**：大部分场景什么都不用写，全局异常处理器就能返回正确的状态码和提示
- **用假服务测异常**：不花钱、结果稳定；升级 Spring AI 或 openai-java 后异常变了，测试会先失败
- **状态存内存**：只是给用户的提示，不是需要保存的事实；存库要在每次调用后多写一次
- **原因码存库而不是提示文字**：提示改了，之前失败的批次也跟着用新的说法

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 各调用方自己捕获 SDK 异常 | 四个地方各写一遍，还要都认识 openai-java 的异常类 |
| 空正文自动重试一次 | 多半每次都一样，只让用户多等 |
| 模型状态存库 | 每次调用多写一次库；重启后的状态不重要 |
| 为查状态真实调用一次模型 | 花钱、慢，设置页每次打开都要等 |
| 抽取批次直接存提示文字 | 提示改了，旧数据还是旧说法 |
| 按用户记录模型状态 | M1 只有一套全局配置，按用户记没有意义；M3 自带 Key 时再按用户 |

## 遗留问题

- 模型状态是全局的，M3 用户自带 Key 后要按用户记录
- 服务重启中断的批次、队列已满的批次没有返回码，前端只显示“这一批没抽出来”
- 降级链（M2）出错时，提示要说明换到了哪个模型
