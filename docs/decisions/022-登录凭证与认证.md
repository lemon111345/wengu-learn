# 022 登录凭证与认证

## 背景

决策 017 定下只保留多用户模式，登录凭证的存放方式留给 #46 比较。要考虑的是：

- 学习对话用 SSE 推送（#19），浏览器的 EventSource 不能设置请求头，带不上 Authorization
- 凭证不能被页面上的脚本读到（XSS）；放在 Cookie 里就要防 CSRF
- 退出登录、修改密码后旧凭证是否立即失效；后端重启后是否要重新登录
- 自部署多一项配置（如签名密钥）、多一个依赖，都是成本

另外，现有代码中 `SourceService`、`ExtractionDraftService` 在 Service 内部调用 `CurrentUser`。登录信息由 Spring Security 放在请求线程上，抽取的后台线程（决策 013）和以后 SSE 的异步线程读不到。

## 决策

### 1. 凭证是服务端 Session

| | 服务端 Session（选用） | Cookie 中的 JWT | 请求头中的 JWT |
| --- | --- | --- | --- |
| SSE | EventSource 自动带 Cookie | 同左 | 带不上，流式接口要改用 fetch 读流 |
| 脚本能否读到凭证 | 不能（HttpOnly） | 不能 | 能（存在 localStorage） |
| CSRF | 要防 | 要防 | 不需要 |
| 退出登录、改密码 | Session 立即失效 | 令牌到期前一直有效，要另加“令牌版本” | 同左 |
| 后端重启 | 要重新登录 | 不用 | 不用 |
| 部署配置、依赖 | 不新增 | 签名密钥、JWT 库 | 同左 |
| 多实例部署 | 要 Spring Session + Redis | 不用 | 不用 |

- Session 存在内存中，空闲 30 天失效（`server.servlet.session.timeout`）；Cookie 为 HttpOnly、SameSite=Lax
- Session 中只存 `LoginUser(id, username)`，不存密码哈希

### 2. 保留 CSRF 保护，令牌放在 Cookie 中

- 用 Spring Security 为单页应用准备的配置（`csrf.spa()`）：令牌放在前端能读到的 Cookie `XSRF-TOKEN` 中，前端在请求头 `X-XSRF-TOKEN` 中带回，服务端核对两者是否一致
- 令牌默认要用到时才生成，GET 请求用不到，Cookie 就一直不写，前端的第一次 POST（登录）会被拒。加一个过滤器，每个请求都读一下令牌
- 缺失或不对时返回 403 `FORBIDDEN`

### 3. 登录接口自己写

- 不用表单登录，也不配置 UserDetailsService 和 AuthenticationManager。`UserService` 校验密码，通过后由 common 的 `LoginSession` 把登录信息存进 Session
- 登录前就有 Session 的，先更换 Session id，防止 Session 固定攻击
- 注册后直接登录：注册页的按钮是“注册并开始”
- 安全配置（`SecurityConfig`、`LoginSession`、`CurrentUser`）放在 common，它们不读用户表；用户、密码、注册开关在 user 模块

### 4. 鉴权失败统一返回 JSON

- 除了注册、登录、退出登录、注册开关查询和健康检查，所有接口都要求登录
- 没有登录返回 401 `UNAUTHORIZED`，不跳转登录页，跳转由前端负责；关掉“登录后跳回原请求”的请求缓存，否则每个未登录的请求都会创建一个 Session
- 登录失败不区分“用户不存在”和“密码错误”，都返回 401 `LOGIN_FAILED`；用户名不存在时也做一次哈希比对，两种情况耗时相同
- 修改密码时当前密码不对返回 400，不用 401：前端收到 401 会当作没登录
- 排除 Spring Boot 的 `UserDetailsServiceAutoConfiguration`，启动时不再生成内存用户、在日志中打印随机密码

### 5. 密码与用户名

- 密码用 `DelegatingPasswordEncoder`（默认 bcrypt），哈希带 `{bcrypt}` 前缀，以后换算法时旧密码照样能校验
- 密码 8～64 个字符，且 UTF-8 编码后不超过 72 字节（bcrypt 只取前 72 字节，超出时 Spring Security 报错）；不去掉首尾空格
- 用户名 2～32 个字符，可以用中文、字母、数字、下划线和连字符（头像取首字）；唯一性按数据库默认的排序规则判断，不区分大小写，以唯一索引为准
- 请求体的 record 重写 `toString`，不打印密码；日志中只记用户 id 和用户名

### 6. 当前用户只在 Controller 中读取

`CurrentUser` 从 `SecurityContextHolder` 读取登录信息，只在 Controller 中使用；Service 一律由调用方传入 userId。`SourceService`、`ExtractionDraftService` 为此改了签名，和 `PlanService`、`UserSettingsService` 一致。

### 7. 修改密码不让其他设备的登录失效

当前设备的 Session 保留。要让其他设备失效，得用 SessionRegistry 记下每个用户的所有 Session，自己写的登录接口还要手动登记，M1 不做。

## 验证

- `AuthControllerTest`（完整过滤器链 + 真实 MySQL）：注册后直接登录；注册时写入默认设置，浏览器时区合法时采用、不合法或没传时用默认；用户名重复（不区分大小写）409；用户名、密码不合规 400（含 25 个汉字超过 72 字节）；中文用户名；密码错误和用户不存在返回同样的 401；没有密码的用户登录不上；退出登录后 401；登录后更换 Session id；未登录访问业务接口返回统一格式的 401；没有 CSRF 令牌 403；从 Cookie 中读出令牌放进请求头能通过；修改密码后只能用新密码登录、当前设备保持登录；当前密码不对时不修改；两个用户的设置和每日计划互不可见；日志中不出现密码
- `RegistrationClosedTest`：注册关闭时注册返回 403、查询结果为未开放、已有用户照常登录
- 测试不用 spring-security-test 的 `csrf()`，改用 `TestCsrf`（Cookie 和请求头放同一个值）：`csrf()` 会把 Spring 上下文中 CsrfFilter 的令牌仓库换成测试用的，而且不会换回来，之后同一个上下文中的请求不再往 Cookie 里写令牌，检查真实流程的测试因执行顺序时过时不过

## 理由

- **Session**：SSE 不用改造，退出登录立即生效，不多配置、不多依赖。M1 单实例部署，“重启后要重新登录”可以接受
- **保留 CSRF**：SameSite=Lax 挡住了跨站的 POST，但挡不住同站的其他子域名；Spring Security 默认开启，关掉反而要自己证明安全
- **自己写登录接口**：只有一种登录方式，标准认证链要多写 UserDetails、UserDetailsService 两个适配类，换来的“认证提供者可插拔”用不上
- **Service 传入 userId**：Service 不依赖登录上下文，在后台线程、异步线程和测试中都能直接调用，不用伪造登录

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| Cookie 中的 JWT | 退出登录、改密码后令牌仍然有效，要加令牌版本；多一个签名密钥和一个依赖 |
| 请求头中的 JWT | 脚本能读到凭证；SSE 要改用 fetch 读流 |
| Session 存进 Redis（Spring Session） | M1 单实例，不需要；M1 的 Docker 部署也不含 Redis（#24） |
| 关闭 CSRF，只靠 SameSite | 同站的子域名挡不住 |
| UserDetailsService + AuthenticationManager | 多两个适配类，好处用不上 |
| 测试中模拟 `CurrentUser`，Service 不改 | Service 用不用登录上下文不统一；SSE 的异步线程仍然读不到 |
| 修改密码后让其他设备的登录失效 | 要用 SessionRegistry 跟踪所有 Session，代码多了不少，M1 不做 |
| 注册后跳到登录页再登一次 | 多一步，没有好处 |
