# 034 多端策略与接口约定

## 背景

用户的主要来源是手机，而 M1 的网页以桌面为主（ui.md 4.3：“不能在窄屏上坏掉”）。以后还可能做一个只负责每日复习的微信小程序，与网页共用后端。

现在不做小程序，但有些后端的做法如果现在不定下来，以后会返工：凭证只能放在 Cookie 里、接口随意改字段、业务规则写在前端。本决策定下多端的方向，以及从现在起新接口要遵守的约定。

## 决策

### 1. 多端策略

- **网页是主力**：桌面优先，手机浏览器可用
- **小程序以后再做**：用 uni-app 单独做一个只负责每日复习的小程序，与网页共用同一个后端；**不为小程序牺牲网页体验**
- **小程序只连接线上版**：小程序要求备案过的 HTTPS 域名，并把域名加入请求白名单，连不了用户自部署的实例
- 小程序目前只在 PRD 的想法池中，不排进里程碑

### 2. 接口与后端约定（从现在起遵守）

规则写在技术方案的“接口与后端约定”一节，这里记录原因：

| 约定 | 原因 |
| --- | --- |
| 接口只做向后兼容的修改：可以新增字段，不删除、不重命名已有字段；确需破坏性修改时新增接口版本，旧版本保留一段时间 | 小程序的旧版本会在用户手机上长期存在，不能强制所有人立刻更新 |
| Service 只接收 userId，不读取 Session | 换一种凭证（如请求头）时，业务代码不用改；后台线程、测试中也能直接调用（决策 022 第 6 条，已经这样做） |
| 日期由后端换算成学习日后返回，客户端不自行计算时区 | 每个客户端都算一遍，迟早算得不一致（已经这样做） |
| 计划、排序、掌握程度等业务规则全部放在后端，客户端只负责显示 | 规则只有一份，小程序不用重写（决策 030、031 已经这样做） |
| 新接口不依赖只有浏览器才有的机制（重定向、Referer 等） | 小程序和其他客户端没有这些 |
| 新设计的耗时 AI 接口优先采用异步方式：提交后返回任务 id，客户端轮询结果 | 手机网络不稳，长连接容易断；小程序的请求有超时限制。已有的同步接口（题目切分、评分建议）暂不改 |
| 微信登录等仅线上版需要的功能，通过配置开关启用，自部署默认关闭 | 自部署和线上用同一套代码（PRD“架构要求”），和 `WENGU_ALLOW_REGISTRATION` 的做法一致 |

### 3. 非浏览器客户端的凭证

决策 022 选了服务端 Session 和 HttpOnly Cookie。小程序的请求不会自动管理 Cookie，以后有非浏览器客户端时，需要支持在请求头中携带凭证。可选方案有两种，**届时用原型验证后再定**：

1. 另建随机令牌：登录时发给客户端，存进数据库，可以随时吊销
2. 让 Spring Session 同时支持从 Cookie 和请求头读取 Session ID，两端共用同一套 Session 存储

使用请求头凭证的请求不需要 CSRF（CSRF 只针对浏览器自动携带的 Cookie）。

已经补进决策 022 的遗留问题。

### 4. 上线前：Session 存进 Redis

决策 022 原来只在“多实例部署”时才把 Session 换成 Spring Session + Redis。现在提前到**上线前必须完成**：Session 存在内存中，每次发版重启，所有线上用户都会掉线。已加入 PRD“上线前必须完成”。

### 5. 手机浏览器：上线前评估

PRD“上线前需要评估”中加入：手机浏览器上的核心路径（今天、学习、评分）是否好用，包括导航能否直接到达、触屏能否顺畅操作。ui.md 的设计原则不在这里修改。

下面是评估时可以参考的建议，**只是建议，未决定**：

| 问题 | 现状 | 建议 |
| --- | --- | --- |
| 导航 | 880px 以下侧栏换到页面最底部，要滚到底才能切换页面 | 窄屏时改成底部标签栏（今天、知识库、导入、设置），学习页照样隐藏 |
| 快捷键提示 | 按钮里的 kbd 提示（Enter、Ctrl Enter）在手机上没有意义 | 触屏设备（`@media (hover: none)`）隐藏 kbd 提示 |
| 发送回答 | 靠 Ctrl Enter 或按钮 | 手机上发送按钮要始终可见，不被虚拟键盘挡住（输入区按可见视口定位） |
| 作答方式 | 打字 | 配合 PRD 的“语音作答第一阶段靠手机输入法”：输入框足够大，长段语音输入后方便修改 |
| 评分 | 四个按钮一行 | 窄屏时排成两行两列，每个按钮至少 44px 高 |
| 浏览器 | 只在桌面 Chrome 上验证过 | 在 iOS Safari、Android Chrome、**微信内置浏览器**上实测：用户常在微信里打开链接，要确认 Cookie、流式回复都正常 |

## 理由

- **网页优先**：一套代码覆盖桌面和手机浏览器，成本最低；小程序只做每日复习这一个高频场景，范围可控
- **现在就定接口约定**：这几条几乎不增加现在的工作量（大部分已经在做），以后能省下大量返工
- **凭证方案留到原型验证**：两种方案各有代价（令牌表 vs Spring Session 的配置），没有真实的客户端时很难判断

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 小程序和网页共用一套前端代码（uni-app 同时出网页） | 网页要用 Element Plus、键盘优先，会牺牲网页体验 |
| 小程序支持连自部署实例 | 微信要求备案域名和请求白名单，做不到 |
| 现在就加请求头凭证 | 还没有非浏览器客户端，两种方案也还没验证 |
| 接口随需求直接改字段 | 小程序旧版本会长期存在 |

## 遗留问题

- 手机浏览器的具体改法，上线前评估后决定（第 5 节）
- 非浏览器客户端的凭证方案，届时用原型验证（第 3 节）
- 接口版本怎么表示（路径前缀还是请求头），第一次需要破坏性修改时再定
