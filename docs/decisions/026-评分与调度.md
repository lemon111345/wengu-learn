# 026 评分与调度

## 背景

#20 把学习闭环的最后一步接上：学完一个知识点后，模型给出评分建议，用户确认四档评分中的一档，交给 FSRS 安排下次复习。设计交接（决策 018、020）又加了几项要求：

- 评分页的按钮下面显示“明天 / 3 天后……”，要有不保存的评分预览
- 选中后立刻显示“X月X日再见”（乐观更新），保存在后台进行
- 日期按用户的学习日（时区和 day_start_hour）返回，前端不用浏览器的日期换算
- review_log 增加评分后的下次到期日；记录“当天完成”（决策 020）

要定的是：AI 建议什么时候生成、存在哪里；预览和实际评分的日期怎么保证一致；“当天完成”在哪一步写；学习日的换算放在哪个模块。

## 决策

### 1. AI 评分建议：同步调用，每个会话只生成一次

- `POST /api/sessions/{id}/rating-suggestion`：第一次调用时用 `rating-suggestion-v3`（temperature 0.2）生成并存库，之后直接返回存好的结果。前端在收到【学习结束】时调用，大约十几到二十几秒
- 输入格式和 #14 实验一致（知识点、类型、要点、整段对话），离线重评的结论才能沿用
- 结果解析失败或没给出评分时重试一次；模型调用本身出错（超时等）不重试。都失败时返回 502 `RATING_SUGGESTION_FAILED`，提示“可以重试，也可以直接评分”
- **评分不等 AI 建议**：用户可以先评分，这时评分流水的 `rating_ai` 为空
- 存在新表 `rating_suggestion`（chat 管理），以会话 id 为主键：评分、判断依据、`weakPoints`（给 #21 复习时针对性提问）、`outOfScopeGaps`（给 #31 整理候选知识点），以及模型、prompt 版本、token 数
- 实验代码中的 `RatingSuggestion` 移到正式代码时改名为 `RatingSuggestionResult`，评分改用 FSRS 的 `Rating`；实验代码保留原样，供以后离线重评

### 2. 评分预览和确认评分

- `GET /api/sessions/{id}/rating-preview`：四种评分分别对应的下次复习日期，不保存
- `POST /api/sessions/{id}/rating` `{rating}`：确认评分，返回选中评分的下次复习日期
- 两者都返回 `{rating, date, days}`：`date` 是学习日，`days` 是距今天几个学习日
- chat 核对会话：属于当前用户、是学习会话（接着问不评分，400）、已经学完（否则 409）、还没评过分（否则 409）。然后交给 review，review 只认 kp_id
- review 在一个事务里更新 card_state、写 review_log（session_id、rating_user、rating_ai、state_before、is_first_review、新增的 `due_after`）
- 一次学习只评一次分：代码中先检查，`review_log.session_id` 的唯一索引兜底，两个请求同时到达时后到的返回 409
- 先读用户设置、再评分：评分已经写进库、之后才出错的话，前端看到失败，实际却评上了

### 3. 预览和实际评分的日期一致

FSRS 默认开启 fuzz（给间隔加随机扰动，避免同一天学的卡总在同一天到期）。随机数如果每次都不同，预览显示“8 天后”，实际评分可能是 7 天或 9 天，前端先显示的“X月X日再见”就对不上。

**fuzz 的随机数改为由“知识点 id + 上次复习时间”决定**：`new Random(Objects.hash(kpId, lastReview))`。同一次评分，预览和实际用的是同一个随机数，日期一致；每次复习的上次复习时间不同，扰动照样分散。为此 `Scheduler` 增加一个接收随机数来源的 `projectDefault(DoubleSupplier)`。

### 4. “当天完成”在算今天的计划时写入

新表 `study_day_completion`（plan 管理），`(user_id, study_date)` 唯一。`GET /api/plan/today` 算出的待复习和待新学都为空、今天又完成过至少一个时，记一条；已经有了就不再写。今天本来就没有任务时不记（决策 020：不计入，也不打断连续）。

### 5. 学习日的换算放到 common，chat 新增依赖 user

预览和评分都要把到期时间换算成学习日，需要用户的时区和 day_start_hour。`StudyDay` 是纯计算，从 plan 移到 `common.time`；chat 从 user 读取设置。user 不依赖任何业务模块，加这一条不会产生环（决策 002 已修订）。

## 理由

- **同步调用**：评分页打开时才需要建议，同步调用就够了，前端一个请求拿到结果。后台生成加轮询多一个状态和一套轮询逻辑，体验并不更好
- **单独一张表**：建议是一个独立的结果，有自己的模型、版本、token 数，#21、#31 都要读；放在会话表上要加五六列，混在会话的状态里
- **评分不等建议**：用户最了解自己，建议只是参考（决策 008）；等建议会让评分页卡住十几秒
- **固定 fuzz 的随机数**：不改 FSRS 的算法，只是让同一次评分的两次计算用同一个随机数；扰动的分布不变
- **在算计划时写“当天完成”**：判断计划是否变空要用 plan 的逻辑。评分在 chat，chat 调 plan 会形成循环（plan 已经依赖 chat）。评分页的“下一个 Enter”本来就要重新取今天的计划，学完最后一个时自然会走到这里
- **StudyDay 放 common**：它不读数据库、不依赖任何模块，plan 和 chat 都要用；放在任何一个业务模块里，另一个都得依赖它

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 学习结束时在后台生成建议，前端轮询 | 多一个状态和轮询，体验和同步调用一样 |
| 建议存在 study_session 的几列中 | 建议有自己的模型、版本、token，混在会话状态里不清楚 |
| 评分按钮等建议出来才能点 | 评分页卡住十几秒；建议只是参考 |
| 关掉 fuzz | 同一天学的卡会总在同一天到期，复习负担集中 |
| 预览时把随机数存下来，评分时取用 | 多一张表或一个缓存；用确定的种子更简单 |
| 评分后立刻检查并写“当天完成” | chat 要调用 plan，形成循环 |
| plan 提供学习日的换算给 chat 用 | chat → plan 形成循环 |
