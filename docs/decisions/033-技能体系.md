# 033 技能体系

> 只写设计，不实现。表结构和功能跟随“默认卡组”所在的里程碑一起实现（里程碑和卡组的内容来源都待讨论），M1 不做任何改动。

## 背景

现在的知识点只有“类型”（决定怎么学），没有“属于哪块技能”。用户看不出自己在 Redis、MySQL、JVM 这些 JD 上会写的技能上分别掌握得怎样，也无法按目标岗位判断还差什么。

另一方面，PRD 一直坚持“不需要配置标签”：用户不该花时间整理分类。原来的表述是“不做标签和分类系统”，这会把“由系统决定的技能归属”也一起排除掉。本次讨论的结论是：**技能归属可以有，但由系统图谱和 AI 决定，用户只确认，不配置。**

## 决策

### 1. 修订“不做标签和分类系统”的表述

PRD 中的“不做标签和分类系统”改为：

> 不做由用户手动创建和维护的标签、分类系统。知识点的技能归属由系统图谱和 AI 决定，用户只确认，不配置。

**修改原因：**原表述的本意是不让用户花时间配置标签，这次修改是让表述更精确，不是推翻原则。技能体系由官方图谱和 AI 判断驱动，用户不需要创建、命名、维护任何分类。

### 2. 三层结构

```
技能图谱（如“Java 后端”）
  └─ 技能（如 Redis、MySQL、JVM；可以有父子关系，最多两层）
       └─ 知识点（现有的 knowledge_point）
```

- 技能的粒度对齐 JD 上会写的粒度
- **图谱和技能多对多**，关系上带重要程度：必会、常考、加分
- **知识点和技能多对多**：新增 `kp_skill` 关联表，设计照搬 `kp_source`：主键 `(kp_id, skill_id)`，冗余 `user_id`，另加“是否主要归属”字段

### 3. 系统级与用户级技能

- **系统级**：来自官方图谱，所有用户共用
- **用户级**：AI 发现官方列表里没有的技能时，创建只属于该用户的技能
- 两种放在同一张 `skill` 表中，`user_id` 为空表示系统级
- **查询这类“系统级与用户级混在一张表”的数据时，必须限定为“系统级，或属于当前用户”**（`user_id IS NULL OR user_id = 当前用户`），避免读到别人的用户级技能。这条同时写进技术方案的“接口与后端约定”

**和“所有业务表都带 user_id”的关系：**规则改为“用户数据表都带 user_id；官方内容（图谱、系统级技能、知识点模板）是全局数据，不带 user_id”。决策 009 和技术方案的“数据模型”同步修订。

### 4. 官方内容：图谱和知识点模板

- 官方图谱和知识点模板以**数据文件形式（如 YAML）放在仓库中**，启动时加载，便于社区通过 PR 贡献
- 官方知识点是**模板**：用户开始学某个图谱时，复制成自己的知识点。之后用户改的是自己的副本，模板不变
- `knowledge_point` 新增**模板 id** 和**模板版本**两个字段，参照 `draft_item_id` 的做法（决策 029：“要点是否改过”“恢复 AI 版本”都拿当前内容和草稿条目对比），支持：
  - “恢复官方版本”：把模板的内容填回编辑框，用户保存后生效
  - “官方内容已更新，是否同步”：模板版本比知识点上记的新时提示
- **模板的稳定标识倾向用 YAML 中人工定义的 slug**（如 `redis.persistence`），不用自增 id：不同的自部署实例各自加载 YAML，自增 id 在每个实例上都不一样，只有 slug 能跨实例对应。启动时同步进数据库表还是只放在内存、最终用什么标识，实现时再定
- 官方内容只使用自己写的、或来源明确允许分享的内容

### 5. 技能归属由 AI 判断，用户确认

- 在抽取流程中，把**官方技能列表作为封闭选项**交给模型选择；列表外的才建用户级技能
- 确认知识点页面上显示 AI 判断的技能，用户确认或修改
- 合并知识点时，被合并者的技能归属并入主知识点（和决策 029 中来源的处理一样）

### 6. 亮度计算

**每个知识点的掌握分：**

- 未学：0
- 已学：当前可提取率 R × min(1, 稳定性 S ÷ 30 天)

**技能亮度 =** 该技能下核心知识点掌握分的平均值。**分母来自官方图谱定义的核心知识点**，没学的按 0 计。

计入规则：

- 不参与调度的类型不计入。按决策 029，是否参与调度看类型，不看有没有 card_state
- 已软删除、已被合并的知识点不计入
- **暂停的知识点：待讨论。**作者的倾向是暂停的官方核心知识点留在分母中、按 0 分计，避免通过暂停变相点亮；以后可能需要一个独立的“不适用于我”标记，处理与目标岗位无关的知识点

其他：

- 亮度**不入库，实时计算**，用户量大了再加缓存
- 界面同时展示**覆盖**（学过多少个知识点）和**牢固**（亮度）。亮度用档位显示，不显示精确百分比，不提供手动点亮

**和决策 030“掌握程度”的区别：**决策 030 的掌握程度特意不用可提取率（“每天都在变，标签会跳”），亮度则有意用它。两个指标回答的问题不同，并存：

| | 掌握程度（决策 030） | 亮度（本决策） |
| --- | --- | --- |
| 回答的问题 | 这个知识点记得牢不牢 | 这个技能现在拿得出手吗 |
| 依据 | 稳定性分档 | 可提取率 × 稳定性 |
| 随时间的变化 | 不复习不会变，评分后才变 | 长期不复习会变暗 |
| 对象 | 单个知识点 | 一个技能下的核心知识点 |

用户按时复习时，可提取率会维持在较高水平，亮度主要由稳定性决定；**只有长期不复习才会明显变暗，这正是亮度要表达的。**界面上为亮度加一句说明，例如“长期不复习，亮度会慢慢变暗”。

### 7. 模块边界

按决策 002，不允许循环依赖：抽取流程（knowledge）要用官方技能列表，亮度计算又要从 knowledge 取知识点。所以拆成三部分：

| 模块 | 内容 | 依赖 |
| --- | --- | --- |
| `skill`（新） | 图谱、技能、知识点模板，加载官方数据文件 | common |
| `knowledge` | `kp_skill` 归它管理（和 `kp_source` 一样）；抽取时取官方技能列表；从模板复制知识点 | 新增 skill |
| `progress`（新，暂名） | 亮度计算 | knowledge、review、skill |

- `progress` 通过 knowledge 的 Service 取“某用户某技能下的知识点 id”，通过 review 的 Service 取“这些知识点当前的可提取率和稳定性”，不直接读对方的表
- review 仍然只通过 kp_id 工作，不知道技能
- 实现时修订决策 002 的依赖表

## 理由

- **由系统决定归属**：用户不用配置，也能按 JD 的粒度看到自己的长短板；“只确认，不配置”守住了 PRD 的原则
- **图谱和技能多对多、带重要程度**：同一个技能在不同岗位上的重要程度不同
- **照搬 kp_source**：已有的、验证过的多对多做法，合并、软删除的规则可以直接套用
- **模板复制成用户的知识点**：用户可以按自己的理解改要点（决策 029），官方更新时又能提示同步，和“AI 原文 → 用户修改”是同一个模式
- **slug**：只有人工定义的标识能跨实例对应
- **亮度用可提取率**：技能的“可用程度”本来就会随时间下降，这是要提醒用户的
- **不入库**：亮度是派生数据，和每日计划一样实时计算（技术方案“每日计划的计算逻辑”）
- **拆成三个模块**：技能定义在最底层，knowledge 和亮度计算都依赖它，没有环

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 用户手动打标签、建分类 | 违背“不需要配置”；用户不会坚持维护 |
| 技能挂在知识点类型上 | 类型决定怎么学，技能决定学的是哪块，是两个维度 |
| 亮度用决策 030 的掌握程度 | 不会随时间变暗，表达不了“很久没复习了” |
| 亮度入库 | 派生数据，可提取率每天都变，存了还要定时更新 |
| 显示精确百分比 | 给人虚假的精确感，也会让人为了数字刷分 |
| 手动点亮 | 亮度要反映真实的记忆，不能由用户声明 |
| 技能定义和亮度计算放在同一个模块 | 和 knowledge 形成循环依赖 |
| 模板用自增 id 关联 | 不同实例上的 id 不一样 |
