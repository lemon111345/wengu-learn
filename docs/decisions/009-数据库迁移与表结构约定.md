# 009 数据库迁移与表结构约定

## 背景

#13 要建出 M1 用到的表。需要定下这几件事：表结构怎么创建和演进，测试用什么数据库，新知识按什么顺序派发，以及时间、枚举、主键等约定。此外，MyBatis-Plus 在原计划中也放在 #13 引入。

## 决策

1. **用 Flyway 管理表结构**：迁移脚本放在 `db/migration`，应用启动时自动执行。已经执行过的脚本不能修改，改表结构一律新建 V2、V3……
2. **V1 只建技术方案中已列出的表和字段**：后面的 issue 需要的字段，在自己的迁移脚本中添加。例如 #19 的“接着问”阶段和有效时长，#20 的 AI 评分建议内容，#15 和 #31 的草稿表
3. **新知识按 `knowledge_point.sort_order` 派发**，相同时按 id。确认草稿时按抽取顺序写入
4. **表结构约定**：
   - 主键 `BIGINT AUTO_INCREMENT`；`card_state` 以 `kp_id` 为主键
   - 时间用 `DATETIME(3)` 存 UTC。JDBC 连接设为 `connectionTimeZone=UTC`，Java 一律用 `Instant`
   - 枚举存名称（如 `CONCEPT`、`GOOD`），不存数字
   - 不建外键，一致性由 Service 保证；需要按它查询的列建普通索引
   - 所有业务表都带 `user_id`，包括 `kp_source` 和 `message`（技术方案原来没列）
5. **默认用户和默认设置写在 V1 中**：用户 id 为 1；每天新学 3 个；4 点作为一天的分界。时区通过 Flyway 占位符读取环境变量 `WENGU_TIMEZONE`，默认 `Asia/Shanghai`，只在第一次建库时生效
6. **测试数据库用 Testcontainers 启动真实的 MySQL 8.4**；本地开发用仓库根目录的 `compose.yaml` 启动 MySQL 8.4
7. **MyBatis-Plus 推迟到 #15 引入**，届时使用 3.5.17（`mybatis-plus-spring-boot4-starter`）
8. **“现在”统一从注入的 `Clock` 获取**（默认 `Clock.systemUTC()`），当前用户 id 由 `common.context.CurrentUser` 提供

## 理由

- **Flyway**：表结构跟着代码一起版本化，空库启动即可建好，每次改动都有记录；新同学、Docker 部署和测试走的是同一套脚本。SQL 写法直观，学习成本低
- **字段随 issue 增量添加**：实现之前不了解细节，提前加的字段大概率要改；有了 Flyway，加字段只是多一个脚本
- **明确的排序字段**：抽取时 AI 按学习顺序输出知识点（决策 006），这个顺序必须保存下来。创建时间相同（一次确认写入多条）或者以后补导入时，按时间排序都不可靠；有了排序字段，以后也能调整顺序
- **UTC + `connectionTimeZone=UTC`**：Connector/J 默认按 JVM 时区写入 DATETIME，在中国的机器上会存成北京时间。测试 `Instant按UTC写入DATETIME` 验证了这一点
- **枚举存名称**：直接查库就能看懂；调整枚举的顺序不会弄乱数据
- **不建外键**：模块之间只通过 Service 交互（决策 002），跨模块的外键会把表绑在一起；删除、合并知识点（#25）时由 Service 统一处理
- **Testcontainers**：要测的正是迁移脚本和时间的处理，H2 的 MySQL 兼容模式在 DDL、时区和函数上都和 MySQL 有差别，测试通过不代表线上可用。代价是运行测试前要先打开 Docker
- **MyBatis-Plus 推迟**：#13 不写 Mapper，提前引入只会多一份没人用的配置。3.5.18 刚刚发布，还跟了一个补丁版，3.5.17 已经稳定了几个月

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 手写建表 SQL，部署时手动执行 | 无法知道库里执行到了哪一版；测试和部署容易不一致 |
| Liquibase | 功能更多，但 XML/YAML 的写法对 M1 来说太重，SQL 脚本已经够用 |
| V1 一次建好所有预计会用到的字段 | 实现前不了解细节，猜出来的字段大概率要改 |
| 按创建时间派发新知识 | 一次确认写入多条时时间相同；无法调整顺序 |
| 测试用 H2 | 与 MySQL 的差异正好落在要测的地方 |
| 默认用户在应用启动时用代码插入 | 要写判断“是否已存在”的逻辑；放在迁移脚本里只执行一次，更简单 |
| 数据库建外键约束 | 与模块边界冲突，删除、合并时还要处理级联 |
