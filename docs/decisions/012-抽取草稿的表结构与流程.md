# 012 抽取草稿的表结构与流程

## 背景

#15 要把导入的题目交给模型抽取知识点。抽取结果不能直接变成知识点：粒度和合并可能不对，用户要先看一遍、取消勾选不要的，确认后才生成知识点（#17）。所以中间需要一份“草稿”。同时 #9 要改进抽取 prompt，需要真实的原始输出，失败的那些尤其重要。

题目怎么切分、怎么导入见[决策 011](./011-题目切分交给模型.md)。

> **修订（#16）**：抽取改为异步、分批，见[决策 013](./013-异步抽取与分批.md)。下面第 1 条中记在草稿上的调用信息（状态、题目、原始输出、失败原因、调用次数、prompt 版本、模型、token）已搬到新的 `extraction_batch` 表，草稿的状态改为由批次推算；第 4、5 条的规则不变，现在按批次执行。接口不再同步返回结果，而是立即返回 RUNNING。

## 决策

### 1. 两张表：草稿和草稿条目

- `extraction_draft`：一次抽取。记录来源材料、状态、发给模型的题目、最后一次的原始输出、失败原因、调用次数、prompt 版本、模型名、token
- `extraction_draft_item`：草稿中的一个知识点。学习顺序、标题、要点、类型、来源题号
- 字段按决策 009 随 issue 增量添加：异步抽取的 RUNNING 状态由 #16 加，条目的勾选状态和确认后的状态由 #17 加，学习会话来源（session_id）由 #31 加。现在 source_id 允许为空，就是为 #31 留的

### 2. 题号沿用 source 中的题号

- 用户只勾选了第 2、5、9 题时，发给模型的仍是 2、5、9，不重新编号
- 题号只在同一份材料内唯一。草稿记录了 source_id，条目的来源题号指的就是这份材料中的题，不会和其他材料的同号题混淆
- 来源题号存成 `"1,3,5"` 这样的字符串，不用 JSON 列加类型处理器：MyBatis-Plus 自带的 JSON 处理器基于 Jackson 2，项目用的是 Jackson 3，混用要多一层配置

### 3. 追问拼在题目后面，抽取 prompt 不变

抽取 prompt v5 的输入仍是每行 `[题号] 题目`。有追问的题拼成一行：`[3] 说说 HashMap 的原理？（追问：为什么容量是 2 的幂？；1.8 为什么引入红黑树？）`；题目中的换行换成空格。草稿的 questions 字段存的就是拼好后实际发给模型的内容。

### 4. 失败也保存草稿，但不把原因返回给前端

- 输出解析失败或校验不通过时重试一次，两次都失败时保存 status 为 FAILED 的草稿；模型调用直接抛异常时不重试，同样保存 FAILED
- 失败的草稿保存最后一次的原始输出和失败原因（校验发现的问题，或异常类名和信息），接口照常返回 200 和草稿，status 为 FAILED、items 为空，前端提示“抽取失败，可以重试”
- error 字段不返回给前端：异常信息可能带有服务商返回的内部细节。给用户看的错误提示由 #27 统一处理
- 这和切分不同（切分失败什么都不保存）：草稿本身就要为 #9 保留数据，而且 source 已经保存，用户可以直接重新抽取

### 5. 原始输出记最后一次，token 累加

- 失败时最后一次的输出最有排查价值；成功时最后一次就是被采用的那次
- token 累加各次调用，反映的是实际费用

### 6. 模型调用在事务外，写库用 TransactionTemplate

- 抽取要 1～3 分钟，放在事务里会一直占着数据库连接。拿到结果后再写草稿和条目，这一步放在一个事务里
- 用 `TransactionTemplate` 而不是 `@Transactional`：保存和调用模型在同一个 Service 里，类内部调用不经过 Spring 代理，`@Transactional` 会悄悄失效。`TransactionTemplate` 把事务的范围直接写在代码里

## 验证

用作者题库的前 20 题（Markdown 表格）走完整流程：导入切分 5 秒，得到 20 道题；抽取 60 秒，一次通过校验，得到 22 个知识点（HashMap、ConcurrentHashMap 的原理题按追问链拆开，其余基本一题一点）。输入 3534 token，输出 12507 token。

## 理由

- **草稿与条目分表**：#17 要逐条勾选、记录哪个知识点来自哪个条目，条目需要自己的 id
- **沿用题号**：#17 确认时直接用来源题号写 kp_source，不用换算
- **失败也存**：真实失败样本是改进 prompt（#9）最有价值的数据
- **TransactionTemplate**：事务边界一目了然，也不用为一个方法单独拆出一个类

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 草稿只用一张表，条目存成 JSON 列 | #17 无法逐条勾选和关联 |
| 勾选后重新编号 1..n | 来源题号要换算回 source 的题号，容易出错 |
| 失败时不保存草稿，直接报错 | 丢失 #9 需要的真实失败数据 |
| 把失败原因返回给前端 | 可能暴露服务商的内部信息；用户也看不懂校验问题 |
| 只记最后一次调用的 token | 低估实际费用 |
| 保存逻辑拆到单独的类上加 @Transactional | 为一个方法多一个类 |
| 整个流程放在一个事务里 | 调用模型时长时间占用数据库连接 |
