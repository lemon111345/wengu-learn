# 016 每日计划与用户设置

## 背景

#18：用户打开计划页，要看到今天该复习哪些、该新学哪些。计算方法在技术方案“每日计划的计算逻辑”中已经定好（实时计算、不建表、分模块查询，见决策 002 第 6 条），本记录补充实现中定下的细节：“今天”怎么算、接口长什么样、设置怎么改。

## 决策

### 1. “今天”是学习日：`StudyDay`

- 学习日从用户时区的 day_start_hour 开始，到第二天的 day_start_hour 为止，换算成 UTC 的 [start, end)。默认 Asia/Shanghai、4 点：北京时间凌晨 3:59 仍属于前一天，熬夜学到凌晨算前一天的
- **比较时刻，不比较小时**：先算出“本地日期的分界时刻”，当前时刻早于它就退回前一天。分界时刻落在夏令时跳过的那一小时里时，`ZonedDateTime` 会往后挪；如果比较小时就会算错
- 夏令时开始和结束的那天，学习日是 23 或 25 小时。分界时刻重复（夏令时结束时回拨的那一小时）时取前一个
- `StudyDay` 是纯函数，放在 plan 中。以后统计（M2）也要用时再考虑移到 common

### 2. 计算步骤和各模块的分工

`PlanService.today(userId)`：

| 步骤 | 模块 | 方法 |
| --- | --- | --- |
| 读设置，算出学习日 | user、plan | `UserSettingsService.get`、`StudyDay.of` |
| 到期复习：last_review 不为空，且 due 早于学习日结束 | review | `dueKpIds(userId, end)` |
| 今天已学的新知识数：is_first_review 为真，reviewed_at 在 [start, end) 内 | review | `countFirstReviews(userId, start, end)` |
| 新知识候选：last_review 为空 | review | `newKpIds(userId)` |
| 去掉暂停的，按 sort_order、id 排列 | knowledge | `activeInOrder(userId, kpIds)` |

- 新知识只取前 `max(0, 每天新学数 − 今天已学数)` 个。**扣除今天已学数是防止重复派发的关键**：不扣的话，下午再打开会再派一批，每天的上限就失效了
- 到期复习也按 sort_order 排，同一主题的复习排在一起
- 每个模块只读自己的表；knowledge 用 IN 查询过滤和排序。MVP 只有几百个知识点，足够快（决策 002 的取舍）
- review 新增 `ReviewLog` 实体，评分时写流水由 #20 完成；目前的测试直接插入流水来模拟

### 3. 接口

- `GET /api/plan/today` 返回 `{date, dailyNewLimit, newLearnedToday, reviews: [{kpId, title, type}], newItems: [...]}`。date 是学习日的日期；**今天已经学完的知识点不在列表中**，只返回 newLearnedToday 计数，页面需要显示“已完成”时（#23）再加
- `GET /api/settings` 返回 `{timezone, dayStartHour, dailyNewLimit}`
- `PATCH /api/settings` 只修改传了的字段，如 `{"dailyNewLimit": 5}`；页面上只露出 dailyNewLimit（#23），不用先读再把另外两个字段传回去
- 校验：timezone 必须是合法的时区 id；dayStartHour 为 0～23；dailyNewLimit 为 0～50（0 表示只复习不学新的，上限防止误填）。不合法时返回 400，同一请求中合法的字段也不保存
- 设置修改后立即生效：计划每次实时计算，没有缓存

## 验证

- `StudyDayTest`：分界前后一分钟（03:59 属于前一天，04:00 属于当天）；用户时区与 UTC 不在同一天（上海、纽约）；分界为 0 点；纽约夏令时开始那天（分界时刻不存在、学习日 23 小时）和结束那天（分界时刻重复、学习日 25 小时）
- `PlanServiceTest`（真实 MySQL，时钟可以手动拨动）：先复习后新学、各自按 sort_order 排列，今天晚些时候到期的算、明天到期的不算；今天学过新知识后名额减少、昨天学的不算；跨过分界时刻后名额恢复；用户时区与 UTC 不在同一天时，按用户时区算今天学过的；修改每天新学数后立即生效，0 时只有复习；今天已学数超过新上限时名额为 0 而不是负数；暂停的、其他用户的知识点被排除
- `UserSettingsServiceTest`：读取默认设置；只改传了的字段；边界值；不合法的值返回 400 且不修改
- 本地开发库：用 #17 确认的 25 个知识点调用接口，返回按学习顺序的前 3 个新知识；把每天新学数改成 5 后立即返回 5 个

## 理由

- **学习日而不是日历日**：很多人晚上学到零点以后，按日历日算，零点一过就会派发新一天的新知识
- **比较时刻**：夏令时的边界情况只在比较时刻时才自然正确，不用写特殊分支
- **PATCH**：页面只改一个字段，PUT 要求传全部字段，前端要多读一次、多传两个它不关心的字段
- **今天学完的不显示**：要显示就得再查一次今天的流水，现在没有页面用到

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 按日历日（零点）切换 | 晚上学到零点以后会被派发新一天的新知识 |
| 比较本地时间的小时 | 分界时刻落在夏令时跳过的那一小时时算错 |
| `PUT /api/settings` 传全部字段 | 页面只露出一个字段 |
| 到期复习按 due 排 | M1 每个知识点一天最多出现一次，最早到期排前面的好处不大；按 sort_order 同主题排在一起 |
| 计划中显示今天已完成的 | 要多查一次流水，目前没有页面需要 |
| StudyDay 放在 common | 现在只有 plan 用，等第二个使用者出现再移 |

## 遗留问题

- 今天已学的知识点如果被暂停（#25），仍计入 newLearnedToday。暂停是少见操作，不处理
- 修改时区或 day_start_hour 会立即改变“今天”的范围，可能让今天的新知识名额多出或少掉一些。属于用户主动修改，不处理
