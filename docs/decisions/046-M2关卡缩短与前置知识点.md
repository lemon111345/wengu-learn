# 046 M2 关卡缩短与前置知识点

## 背景

截至 2026-11-12，`study_day_completion` 仍然为空，按决策 020、038 的口径，“连续自用 14 天”还没有开始计数。M2 能不能结束，取决于这个关卡，不取决于开发量。

同一时间，源码导入实验（#89）第一轮暴露了两个问题：

- **知识点切得太大**：“从 chat 到 review 依次发生了什么”这类链路题有六七个要点，学习时 8 次回答用满还讲不完，复习的 3～5 轮更讲不完
- **前置知识不够**：6 次对话中，大量轮次花在 Flux/Mono、冷流和 `cache()`、SSE、阻塞调用、唯一索引、事务回滚这些通用概念上。评分建议里的“超出范围的缺口”记下了它们，而且很集中

后一个问题，长期的做法是把前置概念做成单独的知识点，排在依赖它的知识点前面学。决策 033 的技能体系里没有“前置关系”，它和技能体系是两件事：

| | 前置知识点 | 技能体系（决策 033） |
| --- | --- | --- |
| 回答的问题 | 学这个知识点之前要先懂什么 | 这个知识点属于哪块技能，这块技能拿得出手吗 |
| 内容来源 | 用户自己的对话（缺口、前置卡） | 官方图谱和知识点模板，依赖默认卡组 |
| 前提 | 无 | 默认卡组的方案（草案）；033“待讨论”的冲突 |

## 决策

1. **M2 的关卡从连续自用 14 天改为 7 天。** 口径不变：按决策 020，从第一个完成全部任务的学习日起算。作者把每天的新知识设为 7 个
2. **前置知识点放进 M2，作为 #31（候选知识点）的扩展**，排在 #90 之后。来源是评分建议的缺口和源码题的前置卡，用户只确认；计划把前置知识点排在依赖它的知识点前面。#31 从“M2 末看数据”改为 M2 必做。具体设计等 #89 第二轮验证完前置卡、出 #31 的方案时再定
3. **技能体系仍在 M3，但可以和 M2 的关卡并行开始**：先讨论决策 033“待讨论”中技能树来源的冲突，再建 M3 的 issue。M2 的关卡只挡 #91 自用数据复盘和 #92 发布 v0.1，不挡开发
4. **组队学习打卡排在 M4 公开上线之后评估**（PRD 想法池原有的安排不变）：它只有在线上版、有真实用户时才有意义

## 理由

- **7 天**：FSRS 的复习大约在 1 天、3 天、一周左右分批回来。前 5 天以新知识为主，复习负担最轻；7 天至少覆盖第一轮复习回来的那一周，能看出“新知识加到期复习”每天做不做得完
- **前置知识点放 M2**：它只用用户自己的对话数据，不需要官方内容，和 #31 的草稿确认流程是同一套；#89 已经说明，没有它，源码题对基础薄弱的学习者太陡
- **技能体系不挪进 M2**：挪进来不会让 M2 结束得更早，只会让 v0.1 要等默认卡组和技能体系做完，也容易重演 M1“建造挤占使用”的问题；而关卡计数的这段时间，开发本来就空着，可以并行开始 M3

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 关卡缩短到 5 天，每天学 10 个 | 5 天测到的是复习最少的一段；每天 10 个新知识，到第二周加上复习，每天很容易超过 3 小时，断一天连续天数就要重算 |
| 关卡保持 14 天 | 多等一周；7 天已经覆盖第一轮复习，第二周的复习量在 #91 复盘时还能继续看 |
| 技能体系整个挪进 M2 | 见理由 |
| 前置知识点等 M3 技能体系一起做 | 前置关系不依赖技能图谱；源码题现在就需要 |
