# 053 评分缺口生成候选知识点

## 背景

#31 要把学习中暴露出来的新内容整理成候选知识点，由用户确认后加入复习。原来的设计（决策 008、018、019）有两个来源：评分建议的 `outOfScopeGaps` 和接着问的对话；决策 046 又加上源码题的前置卡，并要求“计划把前置知识点排在依赖它的知识点前面”。

2026-11-20 作者开发库里的数据：

| 来源 | 数据 |
| --- | --- |
| 评分缺口 | 28 次评分中 22 次带缺口，共 75 条，平均每次 3.4 条、最多 8 条。prompt 要求每条写成可以单独学习的问句（rating-suggestion-v3），已经是题目的形式 |
| 源码题的前置卡 | 19 道源码题，共 19 张卡，#90 已经在第一次学习前显示 |
| 接着问 | 6 次对话 |

两个发现：

- **缺口本身就是题目**，用不上决策 019 的“整理成题目”，可以直接交给现有的抽取
- **缺口量不小，而且同一个知识点每学一次都会冒出相近的缺口**：“单例 Bean 的创建过程”学了 3 次，3 次都有“代理是什么”“构造器注入和 setter 注入的区别”

## 决策

### 1. 第一步只做评分缺口

前置卡转成知识点、接着问的整理（含决策 019 的“整理成题目”和实验）都放到第二步，等这一步自用一段时间、由 #91 的数据决定。

### 2. 在评分页确认题目，勾选的直接生成知识点

- 评分建议出来后，缺口题目跟着显示在评分页，**默认都不勾**
- 勾选后点“加入知识库”：后台对勾选的题跑现有的抽取（粒度规则、类型判断、决策 014 的去重），**抽取完成后自动确认，不再二次确认**
- 被已有知识点覆盖的题（决策 014）不生成，只关联到已有的知识点，评分页写明“知识库里已有”
- 没勾的不生成任何东西，也不留在“等你确认”里
- 一次评分建议的缺口只处理一次

### 3. 生成的知识点排在待学队列的最前面

原知识点刚学完，下次复习至少在一两天后；缺口知识点排在最前面，大概率在那次复习之前学完。这就是决策 046“前置知识点排在依赖它的知识点前面”在缺口场景下的含义，不存前置关系，也不改计划的算法。

今天的新学名额还没用完时，它会在今天就出现，挤掉一道原本派发的题（决策 052 的挤占口径）。

### 4. 存储

- **来源记成一份新类型的材料 `GAP`**：每次“加入知识库”建一份 source，名称“学习缺口：<原知识点标题>”，questions 存勾选的缺口，题号从 1 起。抽取流程照旧，知识库详情的“来源”显示这个名称
- **勾选记录存在 `rating_suggestion` 上（V20）**：`gap_picks`（勾选的是第几条，JSON 数组，从 0 起；还没处理时为空）、`gap_draft_id`（生成的草稿）。没勾的 = 全部缺口减去勾选的
- **自动确认在 knowledge 的抽取后台里**：一份草稿的批次全部成功、材料是 GAP 时，按现有的确认逻辑全部接受，再挪到待学队列最前面（sort_order 设成比现有的最小值还小，可以是负数）。条目的 decision 照常记 ACCEPTED
- **抽取失败时不确认**，草稿停在 FAILED：评分页显示原因和“重试”，今天页的“等你确认”照常显示失败的草稿，重试走现有的接口，成功后自动确认
- **导入页的“最近导入”不显示已确认的缺口草稿**，否则真正的导入会被挤出列表。未确认的（抽取中、失败）照常显示

### 5. 模块分工

chat 校验会话、记下勾选，调用 knowledge 建缺口草稿；knowledge 调用 source 建材料，再走抽取和确认。依赖方向都是已有的（chat → knowledge → source）。

## 理由

- **确认题目而不是知识点**：抽取要再等 30 秒左右，作者通常评完分就按 Enter 进下一题，候选来不及在评分页出现，最后都会堆进“等你确认”，每天多出好几份小草稿要处理。判断“要不要学”，看题目最容易（决策 019 的理由）。也只抽勾选的题，调用更少
- **默认不勾**：“没掌握”的不一定值得单独复习，而且每次有 3～8 条，默认全勾很容易一下加太多。决策 018 让模型的判断决定默认是否勾选，但缺口没有经过“建议加入”这层判断，要模型额外判断就得多一次调用；先不加，自用后看勾选率
- **自动确认**：用户已经在题目层面选过了，再确认一次知识点是重复劳动。要点没经过确认就入库，代价是可能有不准的地方，知识库里可以改，学的时候也会看到
- **GAP 材料类型**：抽取、“来源”显示、去重都不用为它加分支。草稿上直接记会话 id 的话，草稿就没有材料，这几处都要改
- **勾选记在评分建议上**：一次评分建议只有一组缺口、只处理一次，加两列比另建一张表简单；#91 统计勾选率用这两列就够
- **排在最前面而不是最后**：作者有两百多道待学，排在最后要几周后才学到，那时原知识点已经复习过好几次

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 缺口、前置卡、接着问一起做 | 前置卡已经在显示，还没有数据说明要升级成知识点；接着问只有 6 次对话，攒不出实验 |
| 评分建议出来后自动抽取全部缺口，在评分页确认知识点（决策 018、019 原来的设计） | 见理由第一条 |
| 默认全部勾选 | 见理由第二条 |
| 存前置关系，计划按前置关系排序 | 缺口场景下原知识点已经学过，排在最前面就够了；前置卡转成知识点时再看要不要 |
| 草稿上直接记来源会话 | 见理由 |
| 新建一张表记勾选 | 一组缺口只处理一次，两列就够 |

## 遗留问题

- 第二步：前置卡转成知识点、接着问的整理，等 #91 的数据再定，届时另建 issue
- 勾选率太低或太高时，考虑让模型给出“建议加入”并决定默认勾选
