# 014 抽取的去重上下文

## 背景

#16 要求把已有知识点的标题作为上下文传给模型，避免重复抽取。分批之后（[决策 013](./013-异步抽取与分批.md)），同一份资料的不同批次之间也会重复：第 1 批抽出了“HashMap 的扩容机制”，第 3 批里换个问法的题又抽一次。

把标题传给模型容易，难点在于**题目被已有知识点覆盖时，模型输出什么**。原来的校验要求每道题至少对应一个新知识点，传了上下文之后这条不再成立。

本记录是 #16 第三步的前半部分：输出结构、prompt v6、校验和实验。接入抽取流程（读取已有知识点、存储覆盖关系、接口返回）在后半部分完成后补充。

## 决策

### 1. 新增 `covered` 字段表示“已经有了”

```json
{
  "groups": [...],
  "covered": [ { "questionId": 5, "existingIds": ["E3"], "reason": "问法不同，考的是同一内容" } ],
  "knowledgePoints": [...]
}
```

- 已有标题编号为 `[E1] 标题`，用 E 开头和题号区分开；模型在 covered 中引用编号，程序再换回知识点 id 或草稿条目 id
- **一道题可以同时出现在 covered 和新知识点中**，表示部分覆盖：大题拆出的点有些已经有了，剩下的照常输出
- 字段顺序用 `@JsonPropertyOrder` 固定为 groups → covered → knowledgePoints：先分组，再判断哪些已有，最后只输出剩下的

### 2. 上下文的内容和格式

- `DedupContext`（纯函数）：已有知识点在前、同一草稿中已成功批次的条目在后，依次编号；跳过空标题，标题中的换行换成空格
- 只传标题，不传要点：标题本身写成一个问题，信息足够，token 也省
- 用户消息中先列已有知识点，再列题目；**没有上下文时，用户消息和 v5 完全相同**

### 3. 校验规则

- 每道题要么对应至少一个新知识点，要么写进 covered，也可以两者都有；所有题都被覆盖时可以没有新知识点
- covered 中的题号和 E 编号必须存在；引用无效的 covered 不算覆盖。没有上下文时，任何 covered 都无效
- 新知识点的标题不能和已有标题完全相同（忽略空白）。问法不同的重复，程序查不出来，只能靠模型判断

### 4. prompt v6

在 v5 的基础上只做增补，原有规则一字未改：

- 新增“已有知识点”一节：覆盖、部分覆盖、不算覆盖分别是什么；**拿不准时按不算覆盖处理**，因为误判成已有，用户就看不到这个知识点了，比多出一个重复的更难发现
- 处理步骤加上“查已有”；字段说明加上 covered
- 新增示例二（Git 主题，避开样本题和实验题），同时演示完全覆盖、部分覆盖和“相关但不算覆盖”

## 实验

模型 `deepseek-flash`，prompt v6，temperature 0.2。数据只放在 `data-private/`。

### 去重：`DedupExtractionExperiment`

把 v5 抽取 30 道样本题得到的 29 个标题作为已有知识点（E1～E29），再抽取 20 道自己写的新题，按预期打分：

| 类别 | 题数 | 例子 | 判对的标准 |
| --- | --- | --- | --- |
| 完全覆盖 | 8 | “HashMap 扩容的时候具体做了哪些事？”（已有 E2 扩容机制） | 写进 covered、引用预期编号，不再输出新知识点 |
| 部分覆盖 | 4 | “synchronized 和 ReentrantLock 有什么区别？锁升级过程是怎样的？”（区别已有 E6，锁升级是新的） | 写进 covered，同时输出新知识点 |
| 相关但是新内容 | 4 | “Redis 分布式锁和 ZooKeeper 分布式锁有什么区别？”（相关的 E18 是实现方式） | 不写进 covered |
| 无关 | 4 | “什么是零拷贝？” | 不写进 covered |

结果：**3 轮全部判对**（每轮 20/20），没有校验问题；每轮 12 个新知识点，耗时 25～30 秒，输入约 5300 token。

### 回归：v6 不传上下文

用 30 道样本题跑 3 轮，和 v5 的 3 轮比较：

| | 知识点数 | 校验问题 |
| --- | --- | --- |
| v5 | 31、29、29 | 0 |
| v6 | 35、31、29 | 0 |

- 3 轮的 covered 都是空数组，没有凭空编造“已有”
- 拆分数量有差别的只有第 1、26、49、105、165 题，这几道题在 v5 的 3 轮中本来就时拆时不拆（例如第 105 题 v5 为 3/1/1，v6 为 3/3/2）。v6 第 1 轮多出的知识点来自大题拆得更细（“从输入网址到网页显示”拆出了 DNS、TCP 握手），是 #9 想要的方向，不算变差
- 原来的合并（第 1+79、1+3、158+165 题）都保留

## 理由

- **covered 字段**：模型要表达的就是“这道题已经有了，是哪个”。有了结构化的引用，程序能校验编号、换回 id，#17 确认时也能给已有知识点补上与新资料的关联
- **允许部分覆盖**：面试中的大题常常一部分已经学过，一部分是新的；只能“全有”或“全无”的话，要么漏掉新内容，要么重复
- **拿不准时不算覆盖**：两种错误的代价不同。多出一个重复的知识点，用户在草稿中一眼能看到、取消勾选即可；误判成已有，这个知识点就消失了，用户很难发现
- **只做增补**：v5 经过 M0 标注验证，回归实验确认原有的拆分与合并没有变差

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 新知识点上加 `duplicateOf`，由程序删掉 | 模型仍要把重复的内容写一遍，输出更长，含义也绕 |
| 程序按标题相似度去重 | 问法不同的标题字面上很难比出来；语义比较需要向量检索，当前阶段不做 |
| 只允许完全覆盖 | 大题常常部分已学，会漏掉新内容或者重复 |
| 传标题和要点 | token 多一倍以上，实验中只传标题已经全部判对 |
| 用字段名的字母顺序控制输出顺序 | `covered` 会排到 `groups` 前面；`@JsonPropertyOrder` 已在决策 011 中实测有效 |

## 遗留问题

- 实验中的新题是自己写的，“完全覆盖”的题和已有标题的问法差别不算大。真实使用中问法差别更大、或者已有知识点有几百个时的效果，需要在使用中观察
- 已有知识点很多时（比如超过 1000 个）全部传入的 token 成本，到时候再定
- 别的草稿里还没确认的条目不算已有，两份资料先后导入、都还没确认时仍可能重复
