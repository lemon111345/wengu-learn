# 011 题目切分交给模型

## 背景

#15 要把用户粘贴的面试题文本切成一道道题，再交给抽取。最初的方案是规则切分：一行一题，去掉行首编号。但真实资料的格式很乱：作者自己的题库是 Markdown 表格，网上复制的题目带答案、追问、广告、评论区，题库网站的列表页复制下来是“题目 Tab 难度”加上一行一个标签。规则写不全，用户还得先手动整理格式。

模型切分多一次调用，但只需要输出题目、不输出答案，输出很短，成本可以控制得很低。

## 决策

### 1. 导入分两步

1. `POST /api/sources`：保存原文，调用模型切分，返回题目列表供用户预览
2. `POST /api/drafts { sourceId, questionIds? }`：对用户确认的题目调用模型抽取知识点。questionIds 可选，不传则抽取全部；预览时发现多识别了题，直接不勾选，不用重新切分

切分结果存在 source 表，第二步从 source 读取，保证抽取的就是用户预览过的题。

### 2. 切分单独调用一次模型

不合并进抽取 prompt。抽取 prompt v5 的输入格式保持不变（每行 `[题号] 题目`），追问拼在题目后面，例如 `[3] 说说 HashMap 的原理？（追问：为什么容量是 2 的幂？；1.8 为什么引入红黑树？）`。

### 3. 模型只输出题目原文，程序逐字核对

输出格式：

```json
{ "questions": [ { "text": "主问题", "followUps": ["追问 1", "追问 2"] } ] }
```

- 主问题和它的追问算一道题。题号由程序按顺序编，不让模型编
- 字段顺序用 `@JsonPropertyOrder` 固定为 text 在前。Spring AI 生成 JSON Schema 时默认按字母排序（决策 005），followUps 会排到前面；实测这个注解有效
- `SplitValidator`（纯函数）把主问题和每条追问**分别**和原文比对，必须出现在原文中。比对前双方都做规范化：Unicode NFKC，再删掉空白字符和常见的 Markdown 符号（`*` `` ` `` `#` `_` `>`）。这样模型去掉加粗和反引号、改了全半角标点、把跨行的题目拼成一行，都不算失败
- 空题、空追问不通过
- 完全相同的重复题（主问题和追问规范化后都相同）直接去重，不算失败，用户原文中可能本来就有重复。问法不同的题由抽取去合并
- 漏题检查不了，靠用户在预览时发现

### 4. temperature 为 0，重试规则与抽取相同

- 切分只是摘抄，不需要发挥，temperature 设为 0
- 输出解析失败或校验不通过时重试一次；模型调用直接抛异常（网络错误、Key 不对）时不重试
- 两次都失败时什么都不保存，给用户的提示写成能看懂的话（如“题目识别失败，可以重试，或检查原文格式”），详细原因写日志。返回 502 和 `QUESTION_SPLIT_FAILED`：问题出在上游的模型，不是用户的请求

### 5. 上限

- 原文不超过 30000 字，超过时提示用户删掉答案只保留题目，或分批导入。很长的输入按长度切块留给 #16
- 切分后超过 30 题报错，属于业务错误，不重试

### 6. 依赖方向新增 source → llm

切分在 source 里调用模型，修订[决策 002](./002-模块依赖边界.md)。llm 是最底层的模块，加这条依赖不会形成环；切分结果存在 source 表，写入方必须是 source。

### 7. prompt 按版本存放

`resources/prompts/question-split-vN.md`，当前为 v1。示例用 Git 题，避开所有样本的主题。

## 实验

`QuestionSplitExperiment` 显式开启才运行，结果写入 `data-private/experiments/split-时间戳-模型名/`。模型 `deepseek-flash`，prompt v1，temperature 0，每份样本跑 3 次。

| 样本 | 来源 | 题数 | 考察点 |
| --- | --- | --- | --- |
| 01 一行一题 | 自写 | 12 | 混用的编号和列表符号；章节标题不是题 |
| 02 编号加答案 | 自写 | 8 | 答案中的设问句不是题；代码块 |
| 03 Markdown 表格 | 自写 | 14 | 加粗、反引号；一行完全重复 |
| 04 带追问 | 自写 | 7 | `追问：`、`2.1`、`延伸：`、`(1)` 归到正确的题；相关但有独立题号的题单独成题 |
| 05 网页乱格式 | 自写 | 7 | 题目被换行截断；广告、评论区提问、相关推荐 |
| web-1、web-2 | 真实网页复制 | 32、31 | 题库列表页：题目 Tab 难度，标签每个一行，中间夹着重复的表头；一题中有多个问号 |
| all.md 前 30 行 | 作者的题库 | 30 | 真实的 Markdown 表格 |

后三份只放在 `data-private/`，不进仓库。

结果：

- **全部正确**：8 份样本、每份 3 次，题目和追问与预期完全一致，没有校验问题
- **结果稳定**：每份样本的 3 次输出规范化后完全相同
- **成本低**：每次输入约 1300～2200 token，输出约 200～2800 token；耗时通常 1～8 秒，偶尔 10～16 秒
- **计费 token 波动大**：同一样本、输出内容相同，计费的输出 token 可以差好几倍（例如 02 号样本为 476 和 2282，耗时 3 秒和 12 秒）。原始文本的差别只在 JSON 是否缩进，与决策 005 遗留问题中“疑似隐藏推理”的现象一致。不影响正确性，但耗时和费用会偶尔变高

## 理由

- **模型切分**：格式五花八门，规则写不全；切分只输出题目，便宜又稳定
- **逐字核对**：模型最可能出的错是改写或编造题目，程序能完全查出来；规范化让无害的差异不被误判
- **两步导入**：漏题、多题程序查不出，必须让用户先看一眼；勾选题号让剔除多识别的题不用再调一次模型
- **单独调用**：抽取 prompt 已经经过 M0 验证，切分合并进去会改变它的输入和输出，要重新验证；两个任务分开，各自的校验也简单

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 规则切分（一行一题，或空行分隔） | 不支持表格、带答案、网页复制等常见格式，用户要先手动整理 |
| 切分合并进抽取 prompt | 要重新验证抽取效果；预览和勾选无从做起 |
| 模型同时输出答案 | 输出变长、成本变高；抽取 prompt 只用题目，答案留在 source.content 中即可 |
| 模型输出题号或题目在原文中的位置 | 模型数不准位置；逐字核对文本更直接 |
| 只合并连续空白再比较 | 网页复制常在句子中间断行，模型输出时会拼起来，对不上 |
| 切分失败时保存 source 和原始输出 | 留下没有题目的 source；排查用实验入口复现即可 |

## 遗留问题

- 样本都在 32 题以内；超过 30000 字或很多题时的效果，留给 #16 切块时再验证
- 计费 token 波动的原因未查实，同决策 005
