# 037 文档导入

## 背景

PRD 要求导入 PDF / Markdown / DOCX（Must，M1，不做扫描件 OCR）；ui.md 5.7 中“上传文件”和“粘贴文本”走同一个流程：识别题目 → 确认题目 → 抽取知识点。issue #26 要求先用 1～2 份文档做实验，判断是否需要单独的 prompt。

问题在于文档有两类：

- **题目型**：题库、面经，或者“标题就是问题、下面是讲解”的文章（JavaGuide、doocs 这类）。提取出文字后就是粘贴的文本
- **讲解型**：学习笔记、技术文章、书的章节，标题是“核心参数”“拒绝策略”这样的名词，原文中没有现成的题目

## 实验

`DocumentImportExperiment`（DeepSeek deepseek-flash），样本：自己写的线程池笔记（约 3000 字，8 节，标题都不是问题），以及 #16 用过的 JavaGuide 集合文章（7.5 万字，标题多是问题）。#16 已经用现有的识别题目跑过 JavaGuide 文章，直接引用结果。

| 实验 | 结果 |
| --- | --- |
| 笔记 → 现有的识别题目（question-split-v1） | 2 次都是 **0 道**：识别题目只摘抄原文中的问题 |
| JavaGuide 文章 → 识别题目（#16 的结果） | 36 道，正好是问题形式的标题；“集合框架底层数据结构总结”等非问题标题下的内容没有覆盖 |
| 笔记 → 根据内容整理题目（question-generate-v1） | 3 次分别 10、8、9 道，**8 节全部覆盖**，都能用笔记回答，粒度合适；差别只在合并方式 |
| JavaGuide 文章 → 整理题目 | 35 道，覆盖 33 节；原本是问题的标题保留了问法，非问题标题的小节也出了题 |
| 笔记整理出的题 → 现有的抽取（extraction-v6） | 17 个知识点，粒度和题库一致（较大的追问拆成单独的知识点）；部分要点超出笔记（抽取只看题目，要点由模型按自己的知识写，题库导入时也一样） |

结论：讲解型资料**需要单独的“整理题目” prompt**；整理出题目后，**抽取不需要单独的 prompt**。题目清单仍然用识别题目：逐字保留原题、一次最多 200 道，整理会改写问法。

## 决策

### 1. 用户选择资料类型

导入第 1 步加“资料类型”：题目清单（QUESTION，默认）/ 讲解资料（DOCUMENT），粘贴和上传都可以选。存进 `source.type`（列早已是 VARCHAR，注释中就有 DOCUMENT，不需要迁移）。

- 题目清单：现有的识别题目（决策 011）
- 讲解资料：`prompts/question-generate-v1.md`，temperature 0.2。每道题写明依据资料中的哪一节（`section`，原样写标题，没有标题写“无”），`GenerateValidator` 核对这个标题确实在资料中（比对方式同 `SplitValidator.normalize`），防止脱离资料出题；不通过时重试一次，仍失败返回 502 `QUESTION_GENERATE_FAILED`，提示中建议题目清单换成“题目清单”再试
- 整理出的题和识别出的题存成同样的格式（出处只用于核对，不保存），之后的确认、抽取、去重完全不变

### 2. 上传文件：新接口，提取文字后和粘贴一样

`POST /api/sources/upload`（multipart：`file`、`name?`、`type?`），返回和 `POST /api/sources` 相同。名称不填时用去掉扩展名的文件名。

`DocumentTextExtractor`（纯函数）按扩展名提取文字：

| 格式 | 做法 |
| --- | --- |
| PDF | PDFBox 3.0.8，`PDFTextStripper` 按版面位置排序（双栏、文本框多的 PDF 按文件内部顺序会错乱）。有打开密码、没有文字（扫描件）、损坏时给出对应提示 |
| DOCX | POI 5.5.1（不用刚发布的 6.0 大版本），按文档顺序读段落和表格；样式名为“heading N”（中文版 Word 的样式 id 是数字，名称仍是英文）或“title”的段落前加 N 个 `#`，整理题目时模型能看出小节；表格逐行，单元格用 ` \| ` 连接 |
| Markdown、txt | 先按 UTF-8 严格解码（去掉 BOM），不是合法 UTF-8 时按 GB18030（兼容 GBK）解码：国内 Windows 上保存的 txt 常是 GBK |
| .doc 及其他 | 400，提示另存为 .docx |

提取后统一换行、去掉行尾空白、合并连续空行。文件最大 10 MB（`spring.servlet.multipart.max-file-size`，超过时全局异常处理器返回统一格式）；提取出的文字仍受 10 万字上限约束。

### 3. 同步接口

和现有的识别题目一样同步返回（决策 034 说新的耗时 AI 接口优先异步）：这次是在现有同步接口上加一种类型，改异步要连带改第 1、2 步的交互。实测 3000 字的笔记整理 3～9 秒。

## 验证

- 单元测试：`DocumentTextExtractorTest`（测试中用 POI、PDFBox 现场生成 DOCX 和 PDF：标题样式、表格、扫描件、打开密码、损坏文件、GBK 的 txt、不支持的格式）、`GenerateValidatorTest`、`SourceServiceTest`、`SourceControllerTest`（完整过滤器链和 multipart）
- 端到端（DeepSeek）：用 Chrome 把笔记打印成中文 PDF，上传为讲解资料，提取正常（PDF 在句中换行，不影响整理），整理出 9～11 道题；对这份资料发起抽取，39.5 秒得到 13 个知识点。Markdown 题目清单上传后照常识别出 30 道题。11 MB 的文件直连后端返回“文件不能超过 10 MB”
- 页面（无头 Chrome）：类型切换后说明和按钮跟着变；没选文件、选了超过 10 MB 的文件时提示；回上一步文件还在；390 宽不横向滚动

## 理由

- **让用户选**：自动判断要定阈值（识别出的题少于多少就改为整理），而 JavaGuide 这类文章能识别出 36 道题，按阈值会走识别、漏掉非问题小节；用户自己清楚手上的是题库还是笔记
- **整理题目而不是直接抽知识点**：复用确认题目这一步，用户先挑题；抽取、去重、确认的代码和 prompt 都不用动
- **核对出处**：整理出的题不能逐字比对，出处标题是能低成本核对的锚点
- **在后端提取文字**：小程序以后也能直接上传（决策 034）；PDF、DOCX 的解析在 Java 中有成熟的库

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 自动判断资料类型 | 阈值不好定，见上 |
| 讲解资料直接抽取知识点（另写抽取 prompt） | 跳过了用户挑题这一步；抽取 prompt 和去重逻辑要多维护一份 |
| 上传后先把提取的文字填进输入框，让用户修改再提交 | 和 ui.md 不一致，交互多一步；页眉页脚等噪音对整理题目影响不大 |
| 抽取时把资料原文一起传给模型，让要点只依据资料 | 要另做抽取 prompt；题库导入同样不看答案，先保持一致 |
| POI 6.0.0 | 2026-10-22 刚发布的大版本，只用最基础的读段落功能，不值得承担早期问题 |

## 遗留问题

- **要点可能超出资料**：抽取只看题目，要点由模型按自己的知识写。以后可以考虑抽取时附上对应小节的原文
- **PDF 中的标题没有标记**：PDF 提取出的标题只是普通的一行，不像 DOCX 加 `#`；出处核对仍然有效（标题文字在原文中）
- **长资料**：10 万字的讲解资料没有实测整理题目的耗时；用本地模型（上下文 16384）时，长资料可能超过上下文，这时整理题目失败并提示原因（决策 045）
- **开发服务器**：经过 Vite 的开发代理上传超过 10 MB 的文件时，Tomcat 提前断开连接，前端只看到连接失败；前端选择文件时已经先检查大小，部署时经过 Nginx 没有这个问题
- 扫描件 OCR、旧版 .doc 不支持
