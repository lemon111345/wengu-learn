# 041 学习统计最小版

## 背景

M2 的关卡是连续自用 14 天（决策 020、038），界面上却看不到走到第几天（#87）。另外决策 026 留了一个问题：学完最后一个后直接关掉页面，这一天不会记“当天完成”，会直接影响 14 天的计数。

要定的是：“当天完成”怎么在评分后写入，连续天数怎么算，数据从哪个接口给，界面放在哪里。明确不做：统计页、月历热力图、掌握分布、按类型统计用时。

## 决策

### 1. 评分后用 Spring 事件写“当天完成”

- `RatingService.rate` 成功后发布 `StudyRatedEvent(userId)`，事件类放在 chat
- plan 监听这个事件，调用一次 `today(userId)`：计划变空时写完成记录的逻辑只有一份，就是原来那段
- 依赖方向不变：plan 依赖 chat 中的事件类，chat 不知道谁在监听
- 评分事务在 `ReviewService` 中已经提交，用普通的 `@EventListener`。同步监听器抛出的异常会传回发布者，所以监听器要自己捕获并记日志，否则评分已经成功，前端却看到失败
- 打开今天页时的写入保留：暂停或删除最后一个知识点时，计划也会变空，这时没有评分

### 2. 连续天数用纯函数计算，只在需要时查流水

`StudyStreak` 按决策 020 的规则，从昨天往回逐日判断，走到最早一条完成记录为止：

- 有完成记录：加一天
- 没有记录，但当天漏了到期复习：停止
- 没有记录，也没有漏掉的复习：跳过，不计入也不打断
- 今天只在已有完成记录时才加上，还没完成时不判断

“当天漏了到期复习”指：某个知识点在这一天开始前的最后一次评分，`due_after` 早于这一天结束，这一天也没有再评分。review 只查出 kp_id，由 knowledge 过滤暂停、删除和只收录的。只有缺完成记录的日子才查，一路都有完成记录时不查流水。

### 3. 数据放在今天的计划接口中

`GET /api/plan/today` 新增 `currentStreak` 和 `studiedMinutesThisWeek`，只加字段（决策 034）。本周从周一所在的学习日开始算，到今天的学习日结束。

### 4. 今天页右侧栏显示三个数字

“学习时长”面板放在“接下来 7 天”下面，显示今天、本周和连续学习天数。只显示“连续学习 N 天”，不写“N / 14”：14 天是作者这个阶段的关卡，开源后别的用户不需要。

## 理由

- **事件**：唯一既能在后端完成、又不让 chat 依赖 plan 的改法，代码也最少
- **直接调用 `today`**：会多算几个用不上的字段，但只有一条评分触发一次，换来规则只有一份
- **纯函数**：决策 020 的三条规则和“今天还没结束”可以不启动 Spring 直接测
- **不新开接口**：今天页本来就要取计划，前端不用多一个请求和一套加载、失败状态

## 代价

- 暂停的历史没有记录，只能按知识点现在的状态过滤。当时暂停、后来恢复的知识点，可能把那一天误判为打断。这种情况很少，可以接受
- 评分接口多算一次今天的计划，都是按用户查的小查询

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 前端评分后再请求一次计划 | 正好在关页面时可能发不出去；业务规则不该靠客户端（决策 034） |
| 评分接口挪到 plan | 只为这一点把接口和归属都搬走，改动大 |
| 第二天按流水反推当天是否完成 | 新知识的历史推不出来（决策 020） |
| `@TransactionalEventListener` | 事件发布时事务已经结束，这里用不上；发布者在事务中时才需要 |
| 一次读出用户的全部流水，在内存中推算 | 每次打开今天页都要读全部历史；缺记录的日子很少，按天查更省 |
| 单独的统计接口 | 多一个请求和一套加载状态，目前只有今天页用 |
| 界面显示“N / 14” | 14 天是作者的里程碑，不是产品功能 |
