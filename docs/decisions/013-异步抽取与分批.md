# 013 异步抽取与分批

## 背景

#15 的抽取是同步调用：一批题目要 1～3 分钟，请求一直挂着；一次最多 30 题。#16 要把抽取改成后台任务，提供状态查询，超过 30 题时分批抽取，并处理服务重启时还没完成的任务。

草稿的表结构见[决策 012](./012-抽取草稿的表结构与流程.md)，本记录修订其中的第 1 条：原来一份草稿对应一次模型调用，分批之后，一份草稿要调用好几次模型。

#16 分三步完成：第一步异步、状态、重启、重试（第 1～6 条）；第二步分批（第 7 条）；第三步去重上下文，见[决策 014](./014-抽取的去重上下文.md)。

## 决策

### 1. 草稿 = 一次抽取，下面挂批次

- 新增 `extraction_batch` 表。原来记在草稿上的调用信息（状态、发给模型的题目、原始输出、失败原因、调用次数、prompt 版本、模型、token）都搬到批次上，另加进入队列、开始、结束三个时间
- 草稿只剩 user_id、source_id、created_at。条目增加 batch_id，记录来自哪一批
- V4 迁移把已有的草稿各自复制成第 1 批，再删掉草稿上的旧列

### 2. 草稿的状态由批次推算，不存库

- 每个批号取最新的一行：有批次在排队或执行中，草稿为 RUNNING；全部成功为 READY；其余情况为 FAILED，成功批次的条目照常返回
- 批次的状态：PENDING（排队中）、RUNNING、READY、FAILED
- #17 的“已确认”是另一件事，到时候在草稿上单独加字段

### 3. 后台执行：专用线程池，显式提交

- `ExtractionExecutorConfig` 定义线程池 `extractionExecutor`：2 个线程，最多排队 20 个任务
- `ExtractionDraftService` 只处理请求：在一个事务里插入草稿和批次（PENDING），**事务提交之后**再交给 `ExtractionWorker.submit()`。顺序反过来的话，后台线程可能读不到刚插入的批次
- `ExtractionWorker` 在后台按批号顺序执行排队的批次。领取批次时用条件更新（`WHERE status = 'PENDING'`），排队期间已被标为失败的批次不会再执行
- 后台代码不使用 `CurrentUser`，用户 id 一律取自批次。M3 的多用户模式会从请求线程读当前用户，后台线程读不到
- 队列满时不抛异常，这些批次直接标为 FAILED（失败原因“任务队列已满”），接口照常返回草稿，用户稍后重试
- 定义了自己的 Executor 后，Spring Boot 不再自动创建默认的 `applicationTaskExecutor`。用 `spring.task.execution.mode=force` 让它照常创建

### 4. 服务重启时，未完成的批次标为失败，不自动重跑

- 应用启动完成时（`ApplicationReadyEvent`），把所有 PENDING 和 RUNNING 的批次标为 FAILED，失败原因“服务重启，任务中断”
- 用户看到失败后自己点重试
- 这件事由单独的 `ExtractionRecovery` 负责，可以用 `wengu.extraction.recover-on-startup=false` 关掉。不访问数据库的启动方式（实验入口、LLM 实连测试）必须关掉它：启动事件不受懒加载影响，会强制创建监听它的 bean，没有数据库时这个 bean 创建不出来。第一版把监听方法放在 `ExtractionWorker` 上，所有实验入口都启动失败了，普通测试跳过了实验，所以没有发现

### 5. 重试：新增一行，旧行保留

- `POST /api/drafts/{id}/retry` 为每个失败的批号新增一行 PENDING 的批次，题目照抄，批号不变；成功的批次不动
- 失败的旧行保留原始输出和失败原因，供 #9 使用，和决策 012 的“失败也存”一致
- 先 `SELECT … FOR UPDATE` 锁住草稿这一行，两个同时到达的重试请求不会都插入新批次。草稿还在 RUNNING 时返回 409 `CONFLICT`；没有失败的批次时返回 400

### 6. 接口

- `POST /api/drafts` 立即返回草稿，status 为 RUNNING，`batches` 中是 PENDING 的批次
- `GET /api/drafts/{id}` 增加 `batches: [{no, status, questionIds}]`，前端每 3～5 秒轮询一次
- items 只包含成功批次的条目，按批号、批内顺序排列，order 在整份草稿内从 1 连续编号；库中的 item_order 仍是批内的顺序
- 返回码仍是 200，和其他接口一致

### 7. 分批：每批不超过 30 题，题数尽量相等，按顺序执行

- 发起抽取时按原文顺序分批，每批不超过 30 题，各批题数尽量相等：31 题分成 16 + 15，61 题分成 21 + 20 + 20，200 题分成 7 批（29 × 4 + 28 × 3）
- 每份材料最多 200 题（原来是 30 题）
- 后台按批号顺序执行，不并行。去重上下文要用到前面批次的结果，也能减轻服务商的限流压力
- 一批输出解析失败或校验不通过（重试一次后仍不行）时，照常执行下一批
- 一批的模型调用本身出错（网络错误、Key 不对）时，后面还在排队的批次直接标为 FAILED（“前面一批调用模型出错，这一批没有执行”），不再调用模型。这和“调用异常不重试”是同一个道理：后面的批次大概率也会失败，挨个等超时既慢又可能花钱。用户处理好之后重试，所有失败的批次一起重新执行

## 验证

在本地开发库上：

- V4 迁移：决策 012 验证时留下的那份草稿（20 题、22 个条目）变成第 1 批，token、原始输出和条目都保留
- 用真实模型抽取 3 道题：POST 44 毫秒返回 RUNNING，约 10 秒后 READY
- 抽取进行中强行结束进程，再启动：日志输出“1 个未完成的抽取批次已标为失败”，草稿为 FAILED；重试后新增一行，约 12 秒后 READY，失败的旧行保留

## 理由

- **草稿下面挂批次**：用户心里的单位是“导入一份材料、抽取一次、确认一份草稿”，分批只是为了绕开单次调用的上限，不该暴露到 #17 的确认流程和前端。调用信息天然是每次调用一份，放在批次上，字段的含义和决策 012 一致
- **状态推算**：存事实，算派生。草稿和批次各存一份状态，就要保证两者同步
- **显式提交而不是 `@Async`**：和决策 012 不用 `@Transactional` 是同一个原因：类内部调用不经过 Spring 代理，`@Async` 会悄悄失效。显式提交也能直接看出任务从哪里开始执行
- **线程数和队列都设上限**：模型服务商有限流，单用户也用不着更多；队列不设上限，任务多了只会越排越久
- **不自动重跑**：重跑要花钱，用户并不知道；如果正是这个任务把进程搞崩了（比如内存溢出），自动重跑会让应用反复崩溃。重试接口反正要做（单批失败也要用），重启处理直接复用它
- **新增行而不是覆盖**：失败的原始输出是改进 prompt 最有价值的数据
- **按原文顺序、均匀分批**：相邻的题通常属于同一主题，分在一批里模型才能合并（决策 005）；30 + 1 这样的分法会让最后一题单独成批，失去和其他题合并的机会
- **每批 30 题**：抽取 prompt 和 M0 实验都是按 30 题左右验证的，不改动已经验证过的部分

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 任务下面挂草稿，一批一份草稿 | #17 要一批一批确认，或者改成确认整个任务；分批的细节暴露给用户 |
| 草稿和批次各存一份状态 | 要保证两份状态同步 |
| `@Async` | 类内部调用时会失效 |
| 数据库当队列，`@Scheduled` 轮询 PENDING 行 | 天然支持重启和多实例，但多了轮询和抢占逻辑，单实例部署用不上 |
| Redis 或消息队列 | 要新增依赖，对 M1 太重 |
| 任务状态存在内存的 Map 里 | 重启就丢，做不了重启处理 |
| 重启后自动重跑 | 偷偷花钱；可能让应用反复崩溃 |
| 重试时把失败的批次改回 PENDING | 覆盖掉失败时的原始输出 |
| POST 返回 202 Accepted | 语义更准，但和其他接口不一致；前端看 status 就知道要轮询 |
| SSE 推送进度 | 进度几十秒才变一次，轮询更简单；SSE 留给逐字输出的对话 |
| 每批固定 30 题，最后一批放剩下的 | 可能剩下一两题单独成批，失去合并的机会 |
| 各批并行执行 | 快，但前面批次的结果用不上，去重要再调一次模型合并 |
| 一批调用出错后照常执行后面的批次 | Key 错误或网络断开时，每一批都要等到出错，慢，还可能花钱 |

## 遗留问题

- 重启处理的前提是**只部署一个实例**：多个实例时，一个实例启动会把其他实例正在执行的批次也标为失败。部署方案是 Docker Compose 单实例
- 应用已经开始接收请求、但重启处理还没执行的那一瞬间提交的批次，也会被标为失败。窗口只有几毫秒，不处理
- 进程被强行结束时，正在进行的那次调用的 token 和原始输出拿不到，被中断的批次 attempts 为 0
