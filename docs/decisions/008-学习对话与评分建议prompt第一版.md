# 008 学习对话与评分建议 prompt 第一版

## 背景

M1 的学习闭环依赖两个 prompt：学习对话（讲解、提问、追问）和评分建议（对话结束后给出四档评分）。#14 在命令行实验入口中，由作者扮演学生，用 DeepSeek（deepseek-flash）做了两轮实验，每轮 5 个知识点，覆盖 CONCEPT、MECHANISM、COMPARISON 三种类型，熟悉程度从“很熟”到“完全陌生”都有。每学完一个知识点，作者先自评，再看 AI 的评分建议。

**v1 的问题：**

- 对话没有收口：模型讲完就结束，学生从头到尾没有完整回答过一次原题，评分只能凭对话的整体印象
- 评分偏向 HARD（4/5）：v1 规定“被纠正过就是 HARD”，而第一次学习几乎都会被纠正
- 判断依据排在 rating 后面：Spring AI 生成的 JSON Schema 按字段名字母顺序排列，模型按这个顺序输出，依据成了结论之后的解释

**v2 的结果：**

- 新增“完整作答”一步之后，5 个知识点作者都觉得“学懂了”，但完整作答都有明显遗漏。最典型的一例：对话中各个子问题都答对了，完整作答只有一句话。听懂和能讲出来是两回事
- AI 评分 5 个全是 HARD，与自评一致 3/5；对话平均 6.8 次回答（v1 为 4.8 次），只有一次碰到上限，是老师一直追问造成的
- 作者提出两个问题：完全陌生的知识点，轮数上限会不会让人学不透；以及想从面试题倒推着学，遇到不会的就顺着问下去

**离线重评：** 为了区分 prompt 的影响和随机波动，固定已有的 10 份对话记录，用评分 v2 和 v3 各评 3 次（`RerateExperiment`）。去掉 2 份无效记录（一份输入出错，一份对照笔记作答）后，看剩下 8 份：

| | 与自评一致 | 3 次评分都一样 |
| --- | --- | --- |
| 当时的评分（v1 记录用的是评分 v1） | 4/8 | – |
| v2 重评（取 3 次中的多数） | 7/8 | 6/8 |
| v3 重评 | 7/8 | 8/8 |

当时“几乎全是 HARD”，主要来自评分 v1 和随机波动：例如 Redis 那题当时评 HARD，用 v2 重评 3 次有 2 次是 GOOD。v3 的主要收益是稳定。

## 决策

1. **学习对话采用 v2**（`prompts/learning-chat-v2.md`）：摸底 → 讲解 → 检验 → 追问 → **完整作答** → 收尾。不论进行到哪一步，都必须先经过完整作答才能收尾；完整作答只针对知识点标题中的问题，不针对可能更宽的来源题
2. **评分建议采用 v3**（`prompts/rating-suggestion-v3.md`）：
   - 以完整作答为主要依据；第一次学习时被纠正过不降档
   - **以知识点的要点为评分标准**，老师延伸出去的内容没答出来不降档
   - 输出四个字段，字母顺序即输出顺序：`analysis`（先写依据）、`outOfScopeGaps`、`rating`、`weakPoints`
   - `weakPoints` 只放要点范围内没掌握的内容，复习时针对它们提问（#21）
   - `outOfScopeGaps` 放超出要点范围、学生明确表现出不会的内容，每条是一个知识点标题
3. **轮数上限是防止老师追问停不下来的保险，不限制学生**：prompt 建议 4～6 次回答；第 7 次回答后要求完整作答，第 8 次后要求收尾。学生想继续，用下面的“接着问”
4. **M1 新增“接着问”**：收尾、评分之后，学生可以继续自由提问、顺着往下挖。老师只回答、不出题，不影响评分，只设一个防失控的上限。后端会话在 #19 中实现（换用单独的 prompt），页面在 #23 中实现
5. **M1 新增“候选知识点”**：学完后，把 `outOfScopeGaps` 和“接着问”中聊到的新内容整理成候选知识点，由用户勾选确认后生成知识点，复用草稿表和确认流程（#15、#17），不另做一套。为此新建一个 issue，排在 #17、#20 之后；#13 设计草稿表时，草稿的来源要能是“学习会话”，不只是“导入批次”
6. **自动计时要排除不活动的时间**（#19）：超过几分钟没有输入就不计时。实验中各题用时 22～72 分钟，都包含中途离开的时间，无法用来估算每天新学几个
7. **M1 工期调整为约 5 周**（原为 4～5 周），多出的时间用于第 4、5 条

## 理由

- **完整作答是唯一可靠的检验**：“听懂了”的感觉不可靠（流畅性错觉），只有让学生自己完整讲一遍，评分才有依据，也才能发现真正的遗漏
- **以要点为标准**：评分标准如果跟着老师的讲解走，老师追问得越深，学生“遗漏”的就越多，分数反而越低。要点是导入时就确定的、固定的标准
- **不拉长单次对话**：一次能吸收的新内容有限，同样的时间分到多天学效果更好。基础不会的，应当成为单独的知识点，有自己的复习安排，而不是在一次对话里补完
- **“接着问”和“候选知识点”配合**：从面试题倒推着学，目标明确、效率高，但只顺着问而不复习，聊过的内容很快会忘。“接着问”负责往深处挖，“候选知识点”负责把挖出来的内容收进复习计划，两者缺一个都不完整
- **离线重评**：固定对话、只换评分 prompt，才能看出 prompt 本身的效果；每个版本评 3 次，才能把随机波动和真正的差别分开。重评只需调用评分，不需要作者重新学习

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| 去掉轮数上限，或者陌生的知识点放宽上限 | 一次对话越长，学生越疲劳（第 8 次回答时完整作答只剩一句话）；基础不会的问题，拉长对话也解决不好 |
| 不设完整作答，按对话整体印象评分 | v1 证明评分会偏向 HARD，而且看不出学生真正能讲出多少 |
| 老师在摸底时把缺失的基础全部讲完 | 一次对话塞进太多新内容；基础成为单独的知识点才有复习 |
| 每次改完 prompt 都由作者重新学 5 个知识点 | 一轮要几个小时；对话会变，无法把评分的变化归因到 prompt |
| 候选知识点放到 M2 | 只有“接着问”、没有候选知识点，挖出来的内容进不了复习，“接着问”的价值减半 |
| 建“知识点依赖关系”表来管理前置知识 | PRD 中属于 Could；候选知识点加上抽取时的学习顺序已经够用 |

## 已知问题

- 样本少：有效记录只有 8 份，只用了一个模型。自用阶段（M2）按“以用户确认的评分为准，AI 建议同时记录”继续观察准确度
- `outOfScopeGaps` 每次的措辞和条数不同（同一份记录 1～4 条），偶尔会把要点内的内容也算进来。由用户勾选确认来兜底
- v3 的输出比 v2 多约 65%（每次评分约 2.1k 个输出 token），费用仍然很低
- prompt 中“Java 后端面试辅导老师”的角色和“不出手算题”的规则是面向面试的；以后扩展到其他学习方向时，按知识点类型换 prompt 即可，见 PRD“学习原则”
