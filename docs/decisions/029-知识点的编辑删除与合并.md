# 029 知识点的编辑、删除与合并

## 背景

#25 给知识库提供后端操作：编辑标题、类型、要点，暂停与恢复，删除，合并（ui.md 5.9）。前端在 #51，列表和详情接口在 #50。要定的是：

- 删除怎么做，才能支持几秒钟的“撤销”
- 合并后保留谁的调度状态，被合并的学习记录（review_log、会话）怎么处理
- 类型改成或改离只收录的类型（系统设计、个人经历，决策 007）时，card_state 怎么办
- 修改前的内容存在哪里（#9 要用真实的修改数据）

issue 原来写着依赖 #50。实际是 #50 依赖这里：详情要显示“要点是否改过”和合并过来的学习记录，用的是这里定的数据。所以先做 #25。

## 决策

### 1. 数据模型（V11）

| 改动 | 内容 |
| --- | --- |
| `knowledge_point.deleted_at` | 软删除的时间，为空表示没删 |
| `knowledge_point.merged_into` | 被合并时指向主知识点，同时写 deleted_at |
| 新表 `kp_revision` | 每次修改前的快照：kp_id、user_id、type、title、summary、created_at |

- **删除不用 status 表示**：暂停的知识点删除后撤销，要回到暂停。status 原样留着，删除只看 deleted_at
- **快照存修改前的内容**，只在确实有改动时写。AI 的原文在草稿条目中（draft_item_id），按时间排起来就是“AI 原文 → 每次修改前 → 现在”，每一版都能拼出来。“要点是否改过”“恢复 AI 版本”都拿当前内容和草稿条目对比，不另存

### 2. 软删除在查询中显式排除

`KnowledgePointService` 的每个查询都显式加上 `deleted_at IS NULL`：去重上下文、每日计划、今天已完成、知识点总数、学习材料、关联材料。只有 `maxSortOrder` 也算删除的：否则新知识点会用上删除的那个的序号，撤销后两个排序相同。

不用 MyBatis-Plus 的逻辑删除注解 `@TableLogic`：撤销删除时要读出已删除的行，注解会挡住，只能另写 SQL。模块边界保证只有这一个类读这张表，显式写不会漏到别处。

删除只写 deleted_at，**status、card_state、review_log、kp_source 都不动**，撤销后原样回来。删除也就不用调用 review。

### 3. 合并

- 主知识点的标题、要点、类型、排序、复习进度都不变
- 被合并的来源（kp_source）补关联到主知识点，已经有的不重复
- 被合并的软删除，merged_into 指向主知识点
- **被合并的学习记录和 card_state 留在原知识点上，不搬**：那是另一张卡自己的复习序列，搬过来会和主知识点的混在一起，以后按卡优化 FSRS 参数时数据就错了。#50 的详情通过 merged_into 把它们一起显示
- 之前并进被合并者的，merged_into 改指向新的主知识点：被合并的始终指向一个还在的知识点，查学习记录时不用顺着链条找
- 合并没有撤销（ui.md 没有要求）；被合并的不能用“撤销删除”恢复，否则会和主知识点重复

### 4. 改类型时的调度状态

- **改成只收录的类型：card_state 保留**，每日计划在 knowledge 的过滤（`activeInOrder`）中按类型排除。改回来时进度还在，下拉框选错一次没有损失
- **改成参与调度的类型**：没有 card_state 的初始化成新卡，已经有的接着用。为此 review 新增 `ensureCard`；`initCards` 不改，那里重复初始化说明确认草稿出了错，应该失败

这样“有 card_state”不再等于“参与调度”，参与调度看类型。只收录是 M1 的临时状态（ui.md 第 8 节），上线前这两类都要能学，保留的 card_state 那时直接可用。

### 5. 接口

| 接口 | 作用 |
| --- | --- |
| `PATCH /api/knowledge-points/{id}` | 编辑，只改传了的字段 |
| `POST /api/knowledge-points/suspend`、`resume` | 暂停、恢复（批量） |
| `POST /api/knowledge-points/delete`、`restore` | 删除、撤销删除（批量） |
| `POST /api/knowledge-points/merge` | 合并 |

- 都不返回数据：详情的格式由 #50 定，前端操作完重新取列表或详情
- 批量操作在一个事务中：有一个 id 不存在、不属于当前用户或状态不对（已删除、没删除、被合并），整批 404，都不执行
- 删除用 POST 而不用 DELETE：要在请求体中传多个 id，DELETE 的请求体有的代理会丢掉
- “恢复 AI 版本”不单独做接口：前端把 #50 详情中的 AI 原文填回编辑框，用户点“保存修改”，走 PATCH，也留下一条修改记录
- 后端不限撤销删除的时间，前端只在删除后的几秒钟内提供入口

## 理由

- **软删除加撤销**：误删的代价是丢掉复习进度和学习记录，几秒钟的撤销几乎不要成本
- **删除时什么都不动**：撤销只需清空一个字段，不用记住删除前改了什么
- **学习记录不搬**：历史数据保持原样，以后想换一种显示方式只改查询；搬过去就回不来了
- **改类型保留进度**：类型是用户可以随手改的下拉框，改错一次就丢进度不合理

## 放弃的方案

| 方案 | 放弃原因 |
| --- | --- |
| status 加一个 DELETED | 撤销后回不到删除前的状态（暂停） |
| `@TableLogic` 自动过滤 | 撤销时读不到已删除的行；过滤条件藏在注解里，看查询看不出来 |
| 硬删除 | 没法撤销；学习记录变成孤儿 |
| 被合并的学习记录改到主知识点上 | 两张卡的复习序列混在一起，改写了历史 |
| 合并时新建一个知识点 | ui.md 要求选一个主知识点保留它的进度；新建的话进度要从哪个来还得再选 |
| 改成只收录时删掉 card_state（issue 原文） | 选错一次类型，复习进度就没了 |
| `initCards` 跳过已有的 | 确认草稿时的重复初始化是错误，应该失败，不能悄悄跳过 |
| 快照存修改后的内容 | 和存修改前的信息量一样；存修改前的，第一条快照就是用户第一次改之前看到的样子，和 AI 原文对比更直接 |
| 用 DELETE 方法删除 | 请求体有的代理会丢掉 |

## 遗留问题

- 已删除的知识点一直留在库里，M1 不做清理
- 正在学的知识点被删除后，继续对话会返回 404，前端由 #51 处理
- 合并后主知识点的“只收录”判断按它自己的类型，被合并的类型不影响
